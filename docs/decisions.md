## 2026-06-28 · Быстрые подсказки города перед картой СДЭК

**Решение:** Перед сетевым автокомплитом СДЭК добавлен локальный слой подсказок
для частых городов и алиасов. `санк`, `петерб`, `спб`, `питер` сразу показывают
`Санкт-Петербург`; `мск`, `моск`, `moscow` — `Москва`; `ирку` — `Иркутск`;
`новосиб` — `Новосибирск`; `екат`/`екб` — `Екатеринбург`; `нн` — `Нижний
Новгород`. Первая подсказка выбирается по Enter. Ответы `/api/cdek/cities`
кэшируются в браузере и в памяти Node.js 10 минут.

**Почему:** CDEK `/location/cities` не находит часть естественных пользовательских
вводов (`санк`, `петерб`, `ирку`, `новосиб`, `екат`) и отвечает через сеть.
Покупатель ожидает выбрать город после первых букв, не угадывая точное
написание.

**Последствия:** Для частых сценариев выбор города больше не зависит от CDEK API;
карта всё равно открывается по стабильному `city_code` выбранного города.

## 2026-06-28 · Виджет СДЭК ограничен `city_code`

**Решение:** Карта СДЭК остаётся основным UI, но больше не может загрузить
национальный каталог ПВЗ. Checkout монтирует `CdekWidget` только после выбора
города, передаёт `city_code` в `servicePath`, а `/api/cdek/widget?action=offices`
возвращает `400`, если `city_code` отсутствует. Код Москвы исправлен на `44`,
кэш города переведён на `mavita_cdek_city_v2`. На production включено gzip-сжатие
для `application/json` в Nginx.

**Почему:** Боевой виджет без `city_code` делал запрос
`/api/cdek/widget?type=PVZ&is_handout=true&action=offices&page=0` и получал весь
каталог СДЭК по РФ: ~9918 точек, ~18 МБ JSON, ~21 с до полной загрузки. Это
блокировало выбор ПВЗ и оплату.

**Последствия:** Карта загружает точки только выбранного города. Смена города
теперь делается внешним полем checkout над картой; если виджет не стартует,
fallback-список подгружается для того же `city_code`. Ответ Москвы для виджета
остаётся ~1.04 МБ в JSON, но по сети уходит gzip-ом примерно ~141 КБ.

## 2026-06-25 · Виджет СДЭК: Москва по умолчанию + localStorage-кэш + delivery-кэш

**Решение:** Вторая волна ускорения чекаута — три изменения в `app/checkout/page.tsx` и `app/api/checkout/delivery/route.ts`:

1. **Предзагрузка бандла при монтировании страницы** — `import('@cdek-it/widget')` вынесен в отдельный `useEffect([])` без зависимостей. Ранее он стартовал только после того, как delivery API подтверждал `isCdek=true` (последовательно). Теперь бандл качается **параллельно** с запросом delivery API. Экономия ≈ время ответа API (300–500 мс).

2. **Москва по умолчанию** — константа `MOSCOW = { code: 423, city: 'Москва', region: null }`. Как только чекаут убеждается, что СДЭК активен, немедленно вызывает `pickCity(MOSCOW, true)` — город подставлен и ПВЗ начинают грузиться без ожидания IP-ответа. Если IP возвращает другой город — обновляется; если тоже Москву — ничего не меняется.

3. **localStorage-кэш города** (ключ `mavita_cdek_city`, TTL 1 час) — при повторном визите город берётся мгновенно из кэша, `/api/checkout/city` не вызывается. После первого IP-ответа кэш обновляется.

4. **Кэш `/api/checkout/delivery`** — заголовок `public, max-age=30, stale-while-revalidate=300`. Конфиг доставки меняется только через админку; при повторном открытии чекаута браузер отдаёт ответ мгновенно из кэша.

**Почему:** После первой волны (2026-06-24) оставался waterfall: delivery API → isCdek=true → старт загрузки бандла. Для московских пользователей (большинство) город подставлялся только после IP-запроса (~400 мс). Кэш delivery-конфига устранял холодный старт при повторных визитах.

**Последствия:** При изменении тарифа или включении/выключении доставки в админке старый delivery-конфиг может жить в браузерном кэше до 30 с (до 5 мин stale). Это приемлемо — смена конфига не чрезвычайная операция. Кэш IP-города инвалидируется через 1 час или при явной смене города пользователем; при переезде пользователя между визитами может показать неверный город ≤1 ч.

## 2026-06-25 · Оптимизация изображений каталога: sharp + Next.js image optimization

**Решение:** Полная оптимизация фотографий товаров — два независимых слоя:

**Слой 1 — исходники** (`scripts/optimize-images.mjs`):
- Все изображения ресайзятся до max 1600 px по длинной стороне (JPEG quality 85, progressive).
- Фотографии в формате PNG конвертированы в JPEG (11 файлов); `logo.png` с прозрачностью оставлен без изменений.
- 11 строк в `product_images` обновлены миграцией `014_rename_png_catalog_images_to_jpg.sql` (`.png` → `.jpg`).
- Итог: каталог **47 МБ → 7.2 МБ** (−85%). Максимальная экономия на отдельных файлах — 95% (сырые фото 4032×3024 с телефона).

**Слой 2 — Next.js Image Optimization** (`next.config.ts`):
- Убрано `images: { unoptimized: true }`.
- Добавлен `sharp` (npm dep), форматы `['image/avif', 'image/webp']`, `deviceSizes: [640, 828, 1080, 1200, 1600]`.
- `<Image>` теперь автоматически отдаёт AVIF/WebP нужного размера через `/_next/image`. Уже оптимизированные исходники (1600 px) — быстрая отправная точка для генерации кэша.

**Почему:** Фотографии хранились как сырые снимки с телефона (до 2.5 МБ, до 4032×3024 px) и отдавались браузеру без конвертации (`unoptimized: true`). На мобильном соединении страница товара грузила 5–10 МБ только в изображениях.

**Последствия:** `/_next/image` кэш на сервере (`/.next/cache/images/`) прогревается при первом запросе каждой комбинации размер × формат. При `pm2 reload` кэш изображений **сохраняется** (`.next/` не затрагивается rsync). `logo.png` остался PNG — его прозрачность несовместима с JPEG; Next.js отдаст его в WebP/AVIF браузеру автоматически. Скрипт `scripts/optimize-images.mjs` можно запускать повторно при добавлении новых фотографий.

## 2026-06-24 · Виджет СДЭК на чекауте: кэш ответов + предзагрузка бандла

**Решение:** Устранены три источника медленной отрисовки виджета СДЭК на странице оформления заказа:

1. **Серверный кэш ПВЗ** (`lib/cdek.ts` `officesCache`): ответы СДЭК `/deliverypoints` кэшируются в памяти Node.js с TTL 10 минут, ключ — отсортированные параметры запроса (`city_code + type`). Первый посетитель «прогревает» кэш для города — все последующие получают данные мгновенно без обращения к API СДЭК.

2. **Браузерный кэш** (`app/api/cdek/widget/route.ts`): ответы `action=offices` возвращаются с `Cache-Control: public, max-age=600, stale-while-revalidate=60` вместо `no-store`. Повторное открытие чекаута — 0 запросов к серверу.

3. **Предзагрузка бандла** (`app/checkout/page.tsx`): `import('@cdek-it/widget')` стартует сразу как только известно, что виджет нужен (`isCdek && yandexKey`), параллельно с запросом города — а не после двух последовательных рендер-циклов.

Дополнительно: виджет теперь получает `defaultLocation={selectedCity?.city}` (ранее всегда «Москва»), а `loadPointsByCityCode` не вызывается в режиме виджета — лишний запрос к СДЭК API исключён.

**Почему:** Пользователь видел пустой контейнер карты 3–6 секунд: бандл `@cdek-it/widget` (Яндекс.Карты + СДЭК) качался поздно, а СДЭК API на каждый запрос тратил 0.5–2 с. UX — главный приоритет; ожидание на этапе оформления заказа напрямую влияет на конверсию.

**Последствия:** При `pm2 reload` серверный кэш сбрасывается — первый запрос после деплоя снова идёт в СДЭК API (нормально). Кэш живёт в памяти одного PM2-воркера; при масштабировании на несколько воркеров первый запрос каждого воркера холодный.

## 2026-06-22 · Усиление админки товаров (admin-products-hardening)

**Решение:** По итогам ревью закрыты пять дефектов модуля товаров
([docs/specs/done/admin-products-hardening.md](specs/done/admin-products-hardening.md)):
(1) поле `datetime-local` работает в часовом поясе браузера, форма хранит исходный
instant + dirty-флаг и шлёт неизменённый момент как есть (`lib/admin-product-datetime.ts`);
(2) зависимое ограничение скидки проверяется по ИТОГОВОМУ состоянию после
`SELECT … FOR UPDATE`, а DB CHECK `23514` и `SALE_PRICE_INVALID` мапятся в один
контрактный `400`; (3) сортировка фото и cover — одной атомарной операцией,
`PATCH/DELETE /images` возвращают полный `{ images }`; (4) удаление из UI по
умолчанию — архивирование (`visibility='hidden'`), физическое `DELETE` требует
серверно проверенного подтверждения точным `name`; (5) все операции, меняющие
состав/порядок витрины (`POST`/`PATCH`/`DELETE` товара и `reorder`), берут единый
transaction-scoped advisory lock `PRODUCTS_PUBLIC_ORDER_LOCK = 7_903_244_111`
первым запросом транзакции.

**Почему:** прежняя реализация давала неверное локальное расписание скидок, `500`
на валидный частичный PATCH цены при сохранённой скидке, недоступную сортировку
фото, незавершённый сценарий удаления и недетерминированный порядок витрины при
параллельных действиях. Advisory lock берётся для каждого PATCH (а не только при
смене visibility), чтобы исключить гонку «прочитать visibility → решить, нужен ли
lock» и обратный порядок блокировок.

**Последствия:** добавлена команда `npm run test:integration` (реальный PostgreSQL,
schema на запуск, последовательный прогон) и concurrency-/e2e-тесты; release gate
теперь `typecheck && test && test:integration && build && test:e2e`. Схема БД и
маршруты не менялись; advisory key должны брать любые будущие пути, меняющие
`visibility`/`sort_order`.

**Правки после ревью (2026-06-22):** (P0) все фото-операции (`upload`, reorder,
delete) сериализуются на строке `products` через `SELECT … FOR UPDATE` — иначе
гонка delete-последней-обложки против upload оставляла фото без cover; (P1)
календарная валидация дат скидки (Feb 30 не нормализуется, а отвергается); (P1)
concurrency-тест вызывает реальные функции слоя БД через barrier-хук
`__setLockBarrier`; (P1) e2e в CI падает без `DATABASE_URL`, тихий skip запрещён;
(P2) предупреждение о DST-overlap у поля времени — детектор по фактическому offset
до/после перехода (ловит и 30-мин откаты, напр. Australia/Lord_Howe); (P2) hard
delete вынесен в модальный диалог подтверждения (поле/кнопка вне диалога не
показываются). Прогон выполнен на реальном PostgreSQL 16 (Docker): integration
4/4, e2e 4/4, юниты 268, typecheck и build зелёные.

## 2026-06-19 · Стек: Next.js 15 + PostgreSQL + Nginx на одном VPS

**Решение:** Весь магазин на одном VPS (Ubuntu 22.04, 1 vCPU, 1 GB RAM + 2 GB swap). Next.js покрывает и фронтенд (SSR), и API. Отдельный бэкенд-сервер не заводится.

**Почему:** Простота эксплуатации, минимальные затраты, достаточная мощность для 100 товаров и низкого трафика малого магазина. Nginx отдаёт загруженные фото напрямую, минуя Node.js.

**Последствия:** При росте трафика — апгрейд VPS (вертикально), не горизонтальное масштабирование. Приемлемо для горизонта 2 лет.

## 2026-06-19 · Цены в копейках (INTEGER)

**Решение:** Поле `price INTEGER` хранит копейки. Перевод в рубли — только на слое отображения.

**Почему:** Робокасса принимает суммы с двумя знаками после запятой. FLOAT даёт погрешности при умножении и сложении. INTEGER исключает класс ошибок.

**Последствия:** Все вычисления в копейках. В UI: `price / 100` для отображения.

## 2026-06-19 · Аутентификация в админке: iron-session

**Решение:** Один администратор, вход по паролю (без поля логина), зашифрованная cookie через iron-session. Без JWT, без OAuth.

**Почему:** Один владелец-администратор. Простота превыше масштабируемости. iron-session не требует Redis или отдельного сервиса.

**Последствия:** Если понадобится несколько админов — менять на полноценный auth (NextAuth или аналог).

## 2026-06-20 · Деплой на прод: rsync в git-клон, PM2 из подкаталога shop/

**Решение:** На продакшн VPS клонирован полный репозиторий в `/var/www/mavita-repo/`. PM2 запускает `npm start` с `cwd=/var/www/mavita-repo/shop/`. Деплой — rsync локальной `shop/` в `mavita:/var/www/mavita-repo/shop/`, затем `npm run build` + `pm2 reload --update-env`.

**Почему:** GitHub Actions ещё не настроены; rsync — наименьшее трение для ручного деплоя. Полный клон репозитория позволит позже перейти на `git pull` без переезда каталогов.

**Последствия:** `/var/www/mavita/` — мёртвый артефакт провижининга, не используется. При настройке GitHub Actions `cwd` PM2 останется тем же, изменится только источник кода (git pull вместо rsync).

## 2026-06-20 · Робокасса result URL: принимаем и GET, и POST

**Решение:** `app/api/robokassa/result/route.ts` экспортирует оба хендлера (`GET` и `POST`). Логика проверки подписи — общая функция.

**Почему:** В тестовом режиме Робокасса присылает GET-запрос (`.NET Framework/v4.0.30319`), несмотря на то что документация описывает POST. Без GET-хендлера сервер возвращал 405 и заказ не переходил в `paid`. В боевом режиме с включённым POST в ЛК — будет приходить POST; GET остаётся как fallback.

**Особенность:** Робокасса в GET передаёт `OutSum=1800` (без `.00`), тогда как при формировании подписи мы используем `1800.00`. Подпись верифицируется по полученному значению OutSum «как есть» — это корректно, т.к. `MD5("1800:2:pass2")` совпадает с присланной подписью.

## 2026-06-20 · Учёт остатков: не делаем сейчас; вместо него — лимит штук на позицию

**Решение:** Числовой учёт остатков (количество на складе, декремент при оплате) **не вводим**. `products.in_stock` остаётся булевым флагом «есть/нет». Защита от абсурдных корзин — настраиваемый лимит количества одной позиции в заказе (напр. ≤5 шт), который заменит текущий захардкоженный `MAX_QTY=99` в `lib/orders.ts`. Лимит делаем при настройке админки/витрины (Ф4).

**Почему:** Товары — ручная мелкосерийная история (свечи), реального дефицита «последней штуки» с гонкой двух покупателей на горизонте запуска нет. Полноценный складской учёт (атомарный декремент, резерв на время оплаты, возвраты) — заметная сложность, не оправданная текущим объёмом.

**Последствия:** Возможен overselling (TD-21.2): два заказа на «последний» товар оба пройдут оплату — разруливается вручную (возврат). Это осознанный риск. Если объём вырастет или появятся реальные дефициты — вводим `stock_quantity` + атомарное списание при переходе в `paid`.

## 2026-06-20 · CSRF админки: same-origin по хосту, а не по полному origin

**Решение:** `assertSameOrigin` (`lib/auth.ts`, инвариант **I8**) сверяет **хост** заголовка `Origin` с заголовком `Host` (`x-forwarded-host` ?? `host`), без сравнения протокола. Раньше сравнивался полный `Origin` с `new URL(request.url).origin`.

**Почему:** За Nginx `next start` строит `request.url` через внутренний HTTP-сервер → origin получается `http://mavita.ru`, тогда как браузер шлёт `Origin: https://mavita.ru`. Сравнение по протоколу ломало любой изменяющий запрос админки на проде («Неверный Origin», 403); локально на `localhost` не воспроизводилось (TD-22). Доверять `X-Forwarded-Proto` для реконструкции протокола — лишняя зависимость от конфигурации прокси; хост для CSRF достаточен (межсайтовый запрос придёт с другим хостом или без `Origin`).

**Последствия:** Nginx обязан пробрасывать `Host` (`proxy_set_header Host $host;`) — это закреплено в `docs/operations.md` и `architecture.md`. CSRF-защита эквивалентна прежней по силе. Проверено на проде: легитимный вход → 401 на неверный пароль, чужой `Origin` → 403.
