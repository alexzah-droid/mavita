# Журнал решений — МАВИТА-ШОП

Формат: дата · решение · почему · последствия.

## 2026-06-19 · Стек: Next.js 15 + PostgreSQL + Nginx на одном VPS

**Решение:** Весь магазин на одном VPS (Ubuntu 22.04, 1 vCPU, 1 GB RAM + 2 GB swap). Next.js покрывает и фронтенд (SSR), и API. Отдельный бэкенд-сервер не заводится.

**Почему:** Простота эксплуатации, минимальные затраты, достаточная мощность для 100 товаров и низкого трафика малого магазина. Nginx отдаёт загруженные фото напрямую, минуя Node.js.

**Последствия:** При росте трафика — апгрейд VPS (вертикально), не горизонтальное масштабирование. Приемлемо для горизонта 2 лет.

## 2026-06-19 · Цены в копейках (INTEGER)

**Решение:** Поле `price INTEGER` хранит копейки. Перевод в рубли — только на слое отображения.

**Почему:** Робокасса принимает суммы с двумя знаками после запятой. FLOAT даёт погрешности при умножении и сложении. INTEGER исключает класс ошибок.

**Последствия:** Все вычисления в копейках. В UI: `price / 100` для отображения.

## 2026-06-19 · Аутентификация в админке: iron-session

**Решение:** Один администратор, логин+пароль, зашифрованная cookie через iron-session. Без JWT, без OAuth.

**Почему:** Один владелец-администратор. Простота превыше масштабируемости. iron-session не требует Redis или отдельного сервиса.

**Последствия:** Если понадобится несколько админов — менять на полноценный auth (NextAuth или аналог).

## 2026-06-19 · Хранение фото: /public/uploads на диске

**Решение:** Загруженные фото хранятся в `/public/uploads/products/` на VPS. Nginx отдаёт их статикой.

**Почему:** Нет смысла платить за S3 при 20-100 товарах и 10 GB NVMe. Простота.

**Последствия:** При переезде на S3 (>50 товаров или смена хостинга) — менять `filename` в `product_images` на полный URL. Схема БД не меняется.

## 2026-06-19 · Тестовый стенд: общий VPS `147.45.72.20` (alexzah.ru)

**Решение:** Использовать существующий VPS (`147.45.72.20`, `invoice-vps` SSH alias) как тестовый стенд для МАВИТА-ШОП.

**Почему:** VPS уже оплачен и настроен. Экономит время и деньги на этапе разработки.

**Фактическая реализация (2026-06-20):** МАВИТА развёрнута в Docker на порту **4000** (не PM2 на 3002, как планировалось изначально) — PM2 на этом VPS не использовался, выбрали Docker по аналогии с invoice-lifecycle. Контейнер `mavita-shop` + `mavita-db` (PostgreSQL 16-alpine) в сети `mavita-net`. Доступ: `http://147.45.72.20:4000/`. DNS `mavita.alexzah.ru` не настроен — доступно только по IP.

**Последствия:** Нельзя трогать `/opt/invoice-lifecycle/` при деплое МАВИТА. При росте трафика МАВИТА переедет на отдельный VPS.

## 2026-06-20 · Production: выделенный VPS, не shared-хостинг reg.ru

**Решение:** Прод-сервер для `mavita.ru` — выделенный KVM VPS (`45.130.147.108`, Ubuntu 22.04, 1 vCPU, 1 GB RAM, 10 GB NVMe) вместо ранее купленного shared-хостинга reg.ru.

**Почему:** Shared-хостинг reg.ru (`37.140.192.12`) оказался непригодным: Node.js 10 (Next.js 15 требует ≥18), нет root, AlmaLinux 8 вместо Ubuntu. VPS даёт полный контроль при сопоставимой цене.

**Последствия:** Swap 2 GB обязателен (1 GB RAM мало для `npm run build`). Деплой через git pull + PM2, не Docker.

## 2026-06-20 · Деплой на прод: rsync в git-клон, PM2 из подкаталога shop/

**Решение:** На продакшн VPS клонирован полный репозиторий в `/var/www/mavita-repo/`. PM2 запускает `npm start` с `cwd=/var/www/mavita-repo/shop/`. Деплой — rsync локальной `shop/` в `mavita:/var/www/mavita-repo/shop/`, затем `npm run build` + `pm2 reload --update-env`.

**Почему:** GitHub Actions ещё не настроены; rsync — наименьшее трение для ручного деплоя. Полный клон репозитория позволит позже перейти на `git pull` без переезда каталогов.

**Последствия:** `/var/www/mavita/` — мёртвый артефакт провижининга, не используется. При настройке GitHub Actions `cwd` PM2 останется тем же, изменится только источник кода (git pull вместо rsync).

## 2026-06-20 · Робокасса result URL: принимаем и GET, и POST

**Решение:** `app/api/robokassa/result/route.ts` экспортирует оба хендлера (`GET` и `POST`). Логика проверки подписи — общая функция.

**Почему:** В тестовом режиме Робокасса присылает GET-запрос (`.NET Framework/v4.0.30319`), несмотря на то что документация описывает POST. Без GET-хендлера сервер возвращал 405 и заказ не переходил в `paid`. В боевом режиме с включённым POST в ЛК — будет приходить POST; GET остаётся как fallback.

**Особенность:** Робокасса в GET передаёт `OutSum=1800` (без `.00`), тогда как при формировании подписи мы используем `1800.00`. Подпись верифицируется по полученному значению OutSum «как есть» — это корректно, т.к. `MD5("1800:2:pass2")` совпадает с присланной подписью.

## 2026-06-19 · Категории товаров: не делаем сейчас

**Решение:** Таблица `categories` не создаётся в Ф0–Ф4. Витрина — плоский список товаров.

**Вернуться при:** количестве товаров > 20 или явном запросе владельца.
