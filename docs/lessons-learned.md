# Выученные уроки

Короткие выводы из реализации мульти-перевозчиковой доставки и фоновых синхронизаций (2026-06-21). Это обязательный preflight для следующих внешних интеграций.

## Сначала инварианты, затем endpoints

Спецификация не должна ограничиваться happy path («получить данные → сохранить → показать»). До кода нужно письменно зафиксировать:

- источник истины для каждого поля;
- что система **никогда** не должна сделать;
- границу, после которой данные становятся видны пользователю;
- fail-closed/fail-open поведение для каждого отказа.

Для каталога ПВЗ такими инвариантами были: не создать заказ с выключенной или устаревшей доставкой; не удалить ПВЗ из-за усечённого ответа; не публиковать точки неполного прогона; не выдавать успех без подтверждённого уведомления оператору.

## Синхронизация внешних данных — это state machine

Синхронизацию нельзя проектировать как набор upsert-запросов. Для неё заранее описываются состояния и переходы:

`acquire → fetch → stage/mark → validate → publish → retire/soft-disable → success|failed`.

У каждого перехода должны быть владелец, транзакционная граница, fencing для зависших запусков и правило восстановления. Деструктивные действия по данным стороннего API заменяются обратимыми, пока источник не даёт доказуемой полноты ответа.

## Живой контракт API проверяется до выбора архитектуры

Документация провайдера и предполагаемая форма JSON — не контракт. До реализации нужны:

1. живой probe на боевых либо тестовых ключах;
2. обезличенные fixtures реальных ответов;
3. contract-тесты для нормализации, ошибок и ограничений API.

Живой probe на реальных ключах до выбора архитектуры позволяет снять этот риск до начала разработки.

## Failure matrix обязателен до реализации

Для каждого внешнего шага нужно ответить: что будет при timeout, 4xx/5xx, пустом или усечённом ответе, изменении JSON, падении БД, повторном запуске, takeover зависшего worker-а и сбое канала алертов. В матрице фиксируются видимость данных, статус run, повторяемость и способ оповещения.

## Операционный контур — часть готовности, а не приложение к коду

Миграции, ротация ключей, cron/systemd, freshness-gate, мониторинг и независимый канал алертов проектируются вместе с feature. «Написали в stderr» не является алертом; HTTP 2xx не всегда означает подтверждённую доставку сообщения. Rollout должен содержать проверяемые команды, rollback и явно заданные обязательные переменные окружения.

## Тестировать последовательности, а не только отдельные запросы

Моки SQL полезны для контрактов, но не заменяют сценарии состояния:

- `stage → low_overlap` не публикует точки;
- частичный run не влияет на публичную выдачу;
- stale worker не пишет после takeover;
- два пропуска только скрывают точку и последующий возврат восстанавливает её;
- ранний сбой и отказ алерта видны независимому каналу.

Для интеграций с БД хотя бы один набор таких сценариев выполняется на реальном PostgreSQL.

## Практическое правило ревью

Перед объявлением работы завершённой пройтись не по файлам, а по инвариантам и негативным сценариям. Если утверждение звучит как «никогда не потеряем», «всегда уведомим» или «никаких изменений», его нужно проверить сквозным тестом и фактическим кодовым путём, а не только намерением в комментарии.
