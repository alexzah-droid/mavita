## Решение для roadmap

Почта России — не конкурент текущему СДЭК-запуску, а опциональное расширение
покрытия. Брать её в работу только если статистика или бизнес-решение покажут,
что СДЭК/Яндекс недостаточно покрывают нужные направления.

Порядок фаз:

1. **API-revalidation.** Подтвердить официальные endpoints, auth, допустимые
   поля договора, idempotency и повторные операции с реальными учётными данными.
2. **Адресный checkout.** Добавить перевозчика `rupost` как выключенную
   настройку, адресный snapshot и нормализацию адреса до оплаты.
3. **Послеоплатное создание backlog-заказа.** Enqueue в транзакции оплаты,
   worker с идемпотентностью, без синхронных внешних вызовов из ResultURL.
4. **Партии и админка.** Оператор собирает партии; worker выполняет remote
   create/check-in; оператор печатает формы и подтверждает физическую сдачу.

Каждая фаза должна быть отдельной roadmap-задачей с собственными тестами и
release gate. Не реализовывать всё одной большой миграцией/PR.

## Архитектурные инварианты

- `items_kopecks + delivery_kopecks = total_kopecks`; после оплаты тариф не
  меняется и покупателю не предлагают доплату.
- Браузер не является источником истины для тарифа, адреса или выбранного
  перевозчика.
- Внешние вызовы после оплаты идут через outbox/worker, а не из
  `robokassa/result`.
- Трек Почты появляется раньше операционного статуса `handed_to_carrier`, но в
  `orders.tracking_number` попадает только при сдаче перевозчику, чтобы не
  ломать текущий `orders_tracking_number_check`.
- Любая новая ветка delivery должна fail-closed: неполная настройка перевозчика
  делает checkout недоступным, а не создаёт заказ без доставки.

---

## Не брать без отдельного решения

- Live-расчёт тарифа Почты вместо фиксированного тарифа.
- Возвраты.
- Автообновление статусов доставки через tracking API.
- Email-уведомления клиенту с треком.
- Наложенный платёж.
