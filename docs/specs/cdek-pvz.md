# Интеграция СДЭК — выбор ПВЗ при оформлении заказа

Статус: **реализовано в репозитории, выключено конфигурацией**.
Дата актуализации: 2026-06-21.

Текущий rollout использует `DELIVERY_ENABLED=false`: checkout не запрашивает
ПВЗ, не вызывает CDEK API и создаёт заказ с нулевой доставкой. Это позволяет
проверять оплату независимо от внешней интеграции. Включение СДЭК потребует
отдельной Паузы 2, OAuth-ключей и настройки тарифа на production.

## Цель

Дать покупателю выбрать пункт выдачи заказов (ПВЗ) СДЭК на странице оформления.
Код и адрес выбранного ПВЗ сохраняются в нейтральном delivery-snapshot заказа и
показываются покупателю на странице заказа и владельцу в админке. E-mail в этой
фазе не отправляется.

## Решения (зафиксировано)

| Вопрос | Решение |
|---|---|
| Тариф доставки | **Фиксированный или бесплатный** — единая настройка в админке, где `0` означает бесплатную доставку. Без живого расчёта по габаритам. ПВЗ используется только как адрес выдачи. Габариты/вес в `products` не добавляем. |
| Сроки | Продуктовый текст есть на `/delivery`; live-подключение СДЭК пока выключено. |
| Боевой режим | Требует договора с СДЭК и боевых OAuth-ключей. До этого `DELIVERY_ENABLED=false`. |

## Что предоставляет СДЭК

- **API 2.0** — методы списка ПВЗ (`/v2/deliverypoints`) и расчёта (`/v2/calculator`),
  авторизация по OAuth (`client_id` / `client_secret`).
- **Стоимость:** виджет, API и документация — бесплатно. Платится только сама доставка по договору.

В текущей реализации карты/виджета нет: покупатель вводит город, получает список
ПВЗ через `/api/cdek` и выбирает пункт из списка. Это снимает необходимость в
`NEXT_PUBLIC_YANDEX_MAPS_API_KEY`. Секрет CDEK остаётся только на сервере.

## Денежный поток и операционка

Важно различать **два независимых денежных потока**. Покупатель в расчётах с СДЭК
не участвует — он платит только магазину.

### Поток 1: покупатель → магазин (уже реализовано через Робокассу)

Покупатель на сайте платит **всю сумму сразу**: товары + доставка.
Пример: 2 свечи × 1000 + доставка 500 = **2500 ₽**. Предоплата целиком приходит
магазину (Виктория, самозанятая). Доставка для покупателя — просто строка в чеке.

### Поток 2: магазин → СДЭК (отдельный расчёт)

Платит СДЭКу **всегда магазин**, не покупатель. 500 ₽ в заказе — это компенсация
магазину расходов на доставку внутри одной онлайн-оплаты.

| Вариант | Суть | Под нашу схему |
|---|---|---|
| **А. Договор, постоплата** | СДЭК раз в месяц выставляет счёт по факту отправок; магазин платит со своих денег. Есть тариф **для самозанятых**. | ✅ Рекомендуется |
| **Б. Лицевой счёт (предоплата СДЭКу)** | Магазин заранее кладёт деньги на лицевой счёт в СДЭК, стоимость каждой отправки списывается оттуда. | Допустимо |
| **В. Наложенный платёж** | Покупатель платит за товар при получении в ПВЗ; СДЭК переводит магазину за вычетом комиссии (самозанятые ~5%). | ❌ Конфликтует с предоплатой через Робокассу. Опция «оплата при получении» — на будущее |

**Выбрано:** Вариант А (договор, постоплата для самозанятого). Фикс-стоимость доставки
ставим с небольшим запасом — реальная цена у СДЭК может отличаться на ±, разница на магазине.

### Операционка v1 (минимум кода)

При фикс-тарифе (включая `0` для покупателя) создание накладной в СДЭК на первом этапе делается **вручную в личном
кабинете СДЭК** — API создания заказов (`/v2/orders`) не нужен. Магазину достаточно
кода/адреса выбранного ПВЗ из заказа (он уже сохраняется, см. шаг 4). Авто-создание
отправок в СДЭК через API — отдельный этап на потом.

```
Покупатель → 2500 ₽ → Робокасса → магазин          (предоплата за всё сразу)
Магазин    → оформляет накладную (ЛК СДЭК, v1)       → отдаёт заказ в ПВЗ/курьеру
СДЭК       → счёт по факту раз в месяц               → магазин платит СДЭКу
```

## Архитектура

```
checkout (клиент)
   │  виджет СДЭК (servicePath: '/api/cdek')
   ▼
/api/cdek (наш прокси) ──OAuth токен──► api.cdek.ru/v2
   │  (client_secret только на сервере)
   ▼
выбран ПВЗ → код в state
   ▼
POST /api/robokassa/init → createOrder ──проверка кода──► api.cdek.ru/v2
   │
   ▼
orders (нейтральный snapshot ПВЗ)
```

## Шаги реализации

### 1. Конфиг и секреты
`shop/.env.example`:
```
CDEK_CLIENT_ID=
CDEK_CLIENT_SECRET=
CDEK_API_BASE=https://api.cdek.ru/v2
DELIVERY_ENABLED=false
```
При `DELIVERY_ENABLED=false` CDEK credentials не нужны. Значения production не
записываются в документацию и появляются только после отдельного решения включить
интеграцию.

### 2. `shop/lib/cdek.ts`
- `accessToken()` получает и кэширует OAuth token.
- `listPickupPoints(city)` возвращает доступные ПВЗ, `getPickupPoint(code)` повторно
  проверяет выбранный код перед созданием заказа.
- Модуль не обращается к БД и не создаёт накладные.

### 3. `shop/app/api/cdek/route.ts`
- Публичный поиск ПВЗ по городу: получает token и проксирует `/v2/deliverypoints`.
- `client_secret` не уходит в браузер.
- При отсутствии конфига — 503 с понятным сообщением (виджет не показываем).

### 4. БД — миграция `003_orders_delivery_and_admin_events.sql`

Используется единая схема из [admin-orders.md](admin-orders.md):
`delivery_carrier='cdek'`, `delivery_method='cdek_pickup'`, нейтральные
`pickup_point_code/city/name/address`, `delivery_kopecks` и `tracking_number`.
Новые способы доставки не потребуют CDEK-специфичных колонок. `total_kopecks`
равен сумме товаров и `delivery_kopecks`.

### 5. `shop/lib/orders.ts`
- Расширить `OrderInput`: `delivery: { method: 'cdek_pickup', pickupPointCode,
  expectedDeliveryKopecks }` и `expectedTotalKopecks`.
- `validateOrderInput`: требовать выбранный ПВЗ и неотрицательные целые expected
  суммы.
- `createOrder`: серверно подтвердить код ПВЗ, прочитать тариф из
  `store_settings`, записать нейтральные `delivery_*` поля и добавить доставку к
  итогу. Клиентская цена не принимается как источник истины: несовпадение
  expected сумм возвращает `409 PRICE_CHANGED` без создания заказа.

### 6. Фронт — `shop/app/checkout/page.tsx`
- Поле города вызывает `/api/cdek?city=…`; покупатель выбирает ПВЗ из `<select>`.
- В state сохраняется code и клиентское превью выбранного ПВЗ.
- Передавать код и expected суммы в body запроса к `/api/robokassa/init`; адрес
  для snapshot сервер получает заново из API CDEK.
- Блокировать отправку формы, пока ПВЗ не выбран.

### 7. Робокасса — `shop/app/api/robokassa/init/route.ts`
- Собрать `delivery` с кодом ПВЗ и expected суммами из запроса в новый
  `OrderInput`; адрес из браузера не принимать.
- Сумма уже включает доставку (считается на сервере в `createOrder`); `409
  PRICE_CHANGED` возвращает новые суммы и требует повторного нажатия покупателя.
- Опционально: доставку отдельной строкой в фискальный чек Робокассы.

### 8. Отображение ПВЗ
- `shop/app/order/[token]/page.tsx` — адрес ПВЗ нужно показать покупателю после
  включения доставки; текущая DTO страницы пока содержит только состав и итог.
- Админка заказов — адрес ПВЗ в составе заказа. E-mail-уведомления — отдельная
  последующая фаза.

### 9. Публичная страница «Доставка» ✅
- Реализована как `shop/app/delivery/page.tsx` — server-компонент. Текущая стоимость
  доставки берётся из `store_settings` (`getDeliverySettings`, `0` → «бесплатно»),
  `dynamic = 'force-dynamic'`.
- Содержание: способ доставки (ПВЗ СДЭК), стоимость (фикс/бесплатно), сроки, как оплачивается
  (предоплата на сайте, одна сумма товар + доставка), что покупатель **СДЭКу отдельно ничего
  не платит**. Текст — из раздела «Денежный поток» выше.
- Ссылка в шапке (`ShopHeader`) / футере и на странице checkout рядом с выбором ПВЗ.
- Стиль — дизайн-система МАВИТА (фон `#1c1812`, янтарь `#d28a55`, мох `#a8c478`,
  Cormorant Garamond / Manrope).

### 10. Тесты
- `lib/orders.test.ts` — валидация «ПВЗ обязателен», бесплатная доставка,
  серверный источник `delivery_kopecks` и `PRICE_CHANGED`.

## Зависимости и риски

- **Блокер включения:** боевые ключи СДЭК = заключённый договор. До этого
  `DELIVERY_ENABLED=false`; этот режим не требует тестовых ключей.
- Переход на живой расчёт тарифа в будущем потребует добавить вес/габариты в `products`
  и метод `/v2/calculator` в прокси.
