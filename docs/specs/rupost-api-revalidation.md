# Почта России — API-revalidation gate

**Статус:** обязательный preflight перед разработкой.  
**Актуализировано:** 2026-06-30.  
**Цель:** не начинать кодинг Почты России по устаревшей или неполной памяти о
`otpravka.pochta.ru`; сначала подтвердить wire-контракт официальной
спецификацией и реальными учётными данными.

---

## Что уже подтверждено по публичной спецификации

Официальная спецификация `https://otpravka.pochta.ru/specification` остаётся
Angular-приложением со статическими шаблонами методов. На 2026-06-30 в ней
видны ключевые разделы:

- авторизация приложения: заголовок `Authorization: AccessToken <token>`;
- авторизация пользователя: заголовок `X-User-Authorization: Basic <key>`;
- нормализация адреса: `/1.0/clean/address`;
- поиск backlog-заказа: `/1.0/backlog/search`;
- чтение backlog-заказа по id: `/1.0/backlog/{id}`;
- создание/перенос в отправления: `/1.0/user/shipment`;
- чтение отправления по id: `/1.0/shipment/{id}`;
- операции партии: `/1.0/batch/{name}/...`;
- Ф103: `/1.0/forms/{batchName}/f103pdf`;
- check-in: `/1.0/batch/{batchName}/checkin`;
- проверка настроек пользователя: `/1.0/settings`.

Этого достаточно, чтобы оставить Почту в roadmap. Этого недостаточно, чтобы
начинать реализацию без live-проверки.

---

## Что обязательно проверить live

1. **Доступы**
   - API token.
   - User auth key как готовый Base64 `login:password`, а не логин/пароль
     отдельно.
   - `GET /1.0/settings` отвечает для конкретной учётки.

2. **Договорные поля**
   - Допустимые `mail-type`, `mail-category`, `dimension-type`.
   - Можно ли использовать предоплаченный заказ без наложенного платежа.
   - Какие поля отправителя обязательны для формы деятельности владельца.

3. **Нормализация**
   - `POST /1.0/clean/address` принимает реальные адреса покупателей.
   - Какие `quality-code` и `validation-code` считать приемлемыми.
   - Поведение при индексе, который не совпадает с нормализованным адресом.

4. **Backlog/idempotency**
   - Точный метод и путь создания backlog-заказа.
   - Что возвращается: `id`, `barcode`, ошибки по элементам массива.
   - Дедупликация или поиск по `order-num` после timeout.
   - Поведение при повторном `order-num`.

5. **Партии**
   - Точный путь создания партии из remote ids.
   - Когда появляется ШПИ/barcode.
   - Можно ли однозначно прочитать принадлежность каждого заказа к партии через
     `GET /1.0/shipment/{id}`.
   - Повторный check-in: идемпотентен или требует ручного разбора.

6. **Формы**
   - Ф7п для одного отправления: точный путь и входной id.
   - Ф103 по партии: путь, формат PDF, ошибки до/после check-in.

7. **Ошибки и квоты**
   - 401/403 vs 4xx данных vs 5xx/timeout.
   - Ограничения частоты для `clean/address` и создания отправлений.

## Артефакт gate

Перед переходом к [rupost-address-checkout.md](rupost-address-checkout.md) нужно
обновить этот файл:

- дата live-проверки;
- перечень реально вызванных методов;
- curl/Postman snippets без секретов;
- таблица confirmed endpoints;
- список отличий от плановых downstream-спек.

Если хотя бы один критичный пункт неоднозначен, roadmap-статус Почты остаётся
`blocked: needs API clarification`.

---

## Минимальный safe-scope после gate

Если API подтверждён, первую реализацию всё равно резать узко:

- один фиксированный тариф из настроек;
- адресная доставка по РФ;
- нормализация адреса до оплаты;
- после оплаты — только backlog enqueue/worker;
- партии и формы отдельной фазой.
