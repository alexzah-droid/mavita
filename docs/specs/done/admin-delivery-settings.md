## Главное решение: ключи в БД, шифрованные

Сейчас секреты перевозчиков живут в `.env` (`CDEK_CLIENT_SECRET`, `OZON_API_KEY`)
и в браузер не попадают. По решению владельца — **переносим ключи в БД, чтобы
менять их в админке без правки `.env` и reload**. Это меняет модель угроз, поэтому
обязательны правила:

- Секреты хранятся **шифрованными** (AES-256-GCM). Мастер-ключ шифрования —
  **только в `.env`** (`SETTINGS_ENC_KEY`), не в БД. Без него БД-дамп бесполезен.
- Открытый текст ключа **никогда не возвращается в браузер** — ни в API GET, ни в
  серверных props страницы. Наружу идут только: статус «задан/не задан» и
  «хвост» (последние 4 символа) для опознания.
- Ключ принимается только на запись (PATCH). Пустое поле = «не менять».
- Секреты **не логируются** (ни в `console`, ни в `order_admin_events`).

## Что умеет модуль

На странице «Доставка» — карточка на каждого перевозчика (СДЭК, ОЗОН; позже
Яндекс). В карточке:

| Элемент | Поведение |
|---|---|
| Переключатель «Включён» | `enabled` в `store_settings`. Включить нельзя, пока не заданы ключи и тариф (иначе checkout сломается). |
| Поля ключей | СДЭК: `client_id` + `client_secret`; ОЗОН: `client_id` + `api_key`. Секрет показывается маской `••••3f2a`; ввод нового значения перезаписывает, пустое — оставляет старое. |
| Тариф, ₽ | Фикс-стоимость или чекбокс «Бесплатно» (`0`). По перевозчику. |
| Статус | Сводка: `✅ ключи заданы · тариф 350 ₽ · включён` / `⚠️ нет ключей` / `выключен`. |
| Кнопка «Проверить связь» (опц.) | Серверный пинг API перевозчика (список ПВЗ по тестовому городу) — подтверждает, что ключи рабочие, до включения. |

## Семантика включения доставки

Нужно различать три состояния, потому что «доставки нет» и «не смогли прочитать
настройки» — это разные вещи (последнее не должно молча создавать заказ без ПВЗ).
Единый резолвер `resolveDeliveryMode()` (в `lib/store-settings.ts`) возвращает:

| Условие | Режим | Поведение checkout |
|---|---|---|
| `DELIVERY_ENABLED=false` (env) | `disabled` | Аварийный глобальный выключатель. Заказ без ПВЗ, `delivery_kopecks=0`. Перебивает всё. |
| Флаг включён, **нет** ни одного валидного enabled-перевозчика | `disabled` | Легитимно нет доставки → заказ без ПВЗ. |
| Флаг включён, все enabled-перевозчики валидны и есть ≥1 такой перевозчик | `pickup_required` | Требуется выбор перевозчика и ПВЗ. |
| Флаг включён, но настройки **не читаются** (БД недоступна / расшифровка упала / нет `SETTINGS_ENC_KEY`) или есть хотя бы один неисправный enabled-перевозчик | `error` | **503**, оформление недоступно. Никогда не деградирует в «заказ без ПВЗ». |

«Валидный enabled-перевозчик» = `enabled=true` И заданы `client_id`+секрет+тариф И
секрет успешно расшифровывается. **Fail closed:** если хотя бы один
`enabled`-перевозчик неполон или не расшифровывается, весь результат — `error`/503,
даже когда другой перевозчик исправен. Это намеренно: включённый, но невидимо
сломанный перевозчик не должен молча исчезнуть из витрины. Оператор сначала
исправляет его или явно выключает в админке; после этого здоровые перевозчики
снова доступны.

`createOrder` опирается на тот же резолвер, а не на старый `isDeliveryEnabled()`:
в режиме `pickup_required` ПВЗ обязателен; в `disabled` — заказ без ПВЗ; в `error`
бросает `DeliveryUnavailableError` (→503). Это убирает рассинхрон между checkout
и сервером.

## Модель данных — миграции `005_delivery_multi_carrier.sql` и `006_delivery_carrier_secrets.sql`

`004_telegram_order_notifications.sql` уже существует и применяется раньше.
Поэтому порядок миграций фиксирован так:

1. `005_delivery_multi_carrier.sql` — переносит модель заказа на двух
   перевозчиков и добавляет per-carrier тарифы/флаги (работа из
   [ozon-pvz.md](ozon-pvz.md)).
2. `006_delivery_carrier_secrets.sql` — добавляет зашифрованные секреты и
   несекретные id:

```sql
ALTER TABLE store_settings
  ADD COLUMN IF NOT EXISTS cdek_client_id         TEXT,    -- несекретный id
  ADD COLUMN IF NOT EXISTS cdek_client_secret_enc BYTEA,   -- AES-GCM: version|iv|tag|ciphertext
  ADD COLUMN IF NOT EXISTS ozon_client_id         TEXT,
  ADD COLUMN IF NOT EXISTS ozon_api_key_enc       BYTEA;
```

`*_enc` хранит `version(1) | iv(12) | authTag(16) | ciphertext` (см.
[«Шифрование»](#шифрование--shoplibsecret-boxts)). `singleton`-строка одна.
Миграция идемпотентна, существующие заказы не трогает.

### Безопасный порядок (важно)

Наивный вариант ломается: старый `store_settings.cdek_pickup_delivery_kopecks`
создан как `NOT NULL`, а строгая CHECK «`enabled ⇒ ключи+тариф заданы`» и новый
multi-carrier singleton допускают отключённого перевозчика без тарифа. Кроме того,
default `cdek_pickup_enabled=true` привёл бы к строке без ключей. Поэтому:

1. **В `005` снять прежний `NOT NULL` с тарифа СДЭК.** Значение существующих
   строк сохраняется; `CHECK (cdek_pickup_delivery_kopecks >= 0)` продолжает
   запрещать отрицательные значения и допускает `NULL` у выключенного carrier:
   ```sql
   ALTER TABLE store_settings
     ALTER COLUMN cdek_pickup_delivery_kopecks DROP NOT NULL;
   ```
   `shop/sql/schema.sql` обязан описывать уже финальную nullable-модель, иначе
   свежая БД и production после миграций получат разные схемы.
2. **Дефолт флагов — `false`.** В `005` добавить `cdek_pickup_enabled` и
   `ozon_pickup_enabled` с `DEFAULT false`. До явного включения через UI carrier
   не участвует в новом resolver.
3. **Поля nullable** — `006` добавляет `*_id`/`*_enc`; тарифы из `005` тоже
   nullable.
4. **CHECK добавляется `NOT VALID`** — не проверяет уже существующие строки:
   ```sql
   DO $$ BEGIN
     IF NOT EXISTS (SELECT 1 FROM pg_constraint
                    WHERE conrelid = 'store_settings'::regclass
                      AND conname = 'store_settings_cdek_complete_check') THEN
       ALTER TABLE store_settings ADD CONSTRAINT store_settings_cdek_complete_check
         CHECK (cdek_pickup_enabled = false
                OR (cdek_client_id IS NOT NULL AND cdek_client_secret_enc IS NOT NULL
                    AND cdek_pickup_delivery_kopecks IS NOT NULL)) NOT VALID;
     END IF;
   END $$;
   -- аналогично для ozon и для прочих новых constraints
   ```
5. **Заполнение ключей** — оператор вводит боевые ключи через UI или применяет
   одноразовый backfill из старого `.env`, затем включает перевозчика.
6. **`VALIDATE CONSTRAINT`** — после того как все enabled-строки заполнены:
   ```sql
   ALTER TABLE store_settings VALIDATE CONSTRAINT store_settings_cdek_complete_check;
   ```

`ADD COLUMN IF NOT EXISTS` и проверка имён constraints — обязательны: миграции
заявлены как идемпотентные и должны безопасно повторяться после прерванного deploy.
`NOT VALID` не освобождает от проверки **новых** `INSERT`/`UPDATE`, поэтому
backfill и включение carrier выполняются только после заполнения полного набора.

### Rollout без скрытого выключения доставки

Нельзя сначала выпустить новый resolver с пустыми DB-credentials и рассчитывать
на старый `.env`-fallback: новый runtime намеренно не читает `CDEK_CLIENT_SECRET`.
Правильный порядок для уже работающего СДЭК:

1. Сделать backup БД; убедиться, что `SETTINGS_ENC_KEY` задан и декодируется в 32
   байта. Старые `CDEK_CLIENT_*` пока **не удалять**.
2. Применить `005`, затем `006`. Старое приложение продолжает работать от `.env`,
   так как код runtime ещё не менялся.
3. Запустить одноразовую server-side команду `scripts/backfill-delivery-credentials.ts`:
   она берёт существующие переменные окружения только из процесса, шифрует их,
   записывает singleton под `FOR UPDATE`, выставляет СДЭК `enabled=true`, сохраняет
   прежний тариф и затем проверяет расшифровку. Команда не печатает значения и
   завершается ошибкой, если тариф/ключи отсутствуют. Альтернатива — ввести ключи
   в UI, проверить связь и включить carrier, пока старый runtime ещё обслуживает
   витрину.
4. Проверить `/api/checkout/delivery` и оформление тестового заказа, затем
   выпустить код, который читает только DB-credentials. Откат возможен, пока
   старые env-ключи сохранены.
5. После подтверждённого rollout удалить старые `CDEK_CLIENT_SECRET`,
   `CDEK_CLIENT_ID`, `OZON_API_KEY` и `OZON_CLIENT_ID` из `.env`.

Если выбранное окно требует выключить доставку, оператор обязан сначала выставить
`DELIVERY_ENABLED=false`; только этот глобальный выключатель легитимно создаёт
заказы без ПВЗ.

## Шифрование — `shop/lib/secret-box.ts`

```
encryptSecret(plain, aad): Buffer   // AES-256-GCM → version(1)|iv(12)|tag(16)|ciphertext
decryptSecret(buf, aad): string     // обратно; бросает при неверном tag/version/aad
maskSecret(plain): string           // '••••' + последние 4 символа, для UI
```

- **Мастер-ключ:** `SETTINGS_ENC_KEY` из `.env`. Декодированная длина — **ровно 32
  байта** (AES-256), не «≥32». Формат: 64 hex-символа или base64; при старте
  сначала распознать строго как hex (`/^[0-9a-f]{64}$/i`), иначе как canonical
  base64, декодировать и проверить `length === 32`, иначе бросить (как `assertAuthConfig`
  для `SESSION_SECRET`). «≥32 символа» от `SESSION_SECRET` сюда не переносить — там
  про длину строки, здесь про длину ключа в байтах.
- **Версионирование:** первый байт — версия формата (`0x01`). Позволит сменить
  схему (другой алгоритм/длина) без неоднозначности при чтении старых значений.
- **AAD (additional authenticated data):** шифруем с привязкой к назначению —
  `aad = "<carrier>:<field>"` (напр. `cdek:client_secret`). GCM проверяет AAD при
  расшифровке, поэтому шифртекст нельзя переставить между полями/перевозчиками
  (скопировать `ozon_api_key_enc` в `cdek_client_secret_enc` — расшифровка упадёт).
- Каждый вызов — **новый случайный IV** (12 байт). IV не секретен, хранится рядом.
- Без `SETTINGS_ENC_KEY` запись/чтение секретов невозможны — модуль отдаёт
  понятную ошибку, перевозчики считаются недоступными (режим `error` → 503, см.
  [семантику](#семантика-включения-доставки)).

### Ротация мастер-ключа

Формат ciphertext версионирован, но не содержит key-id: ротация выполняется как
контролируемая офлайн-операция, а не сменой переменной в работающем процессе.
До первого production-секрета в `operations.md` и в репозитории должен появиться
проверяемый скрипт `scripts/rotate-delivery-settings-key.ts` и следующая процедура:

1. backup БД; включить maintenance и остановить все app/worker-процессы;
2. временно задать одновременно `SETTINGS_ENC_KEY_OLD` и новый
   `SETTINGS_ENC_KEY`; скрипт под блокировкой singleton расшифровывает все
   delivery-secrets старым ключом, шифрует новым ключом и в конце проверяет каждый
   результат;
3. при ошибке транзакция откатывается, старый ключ остаётся рабочим; при успехе
   удалить `_OLD`, запустить приложение только с новым ключом;
4. rollback после успешного commit — восстановление backup БД **и** старого ключа,
   поэтому ключ нельзя менять без сохранённого backup.

Во время ротации PATCH, `/test` и checkout недоступны; это осознанное короткое
maintenance-окно, а не тихая деградация заказа до доставки `0`.

## Слой настроек — `shop/lib/store-settings.ts`

Обобщить под перевозчиков (продолжение шага 5 из [ozon-pvz.md](ozon-pvz.md)):

```ts
type CarrierSettings = {
  enabled: boolean
  hasSecret: boolean          // наружу: задан ли ключ
  secretMask: string | null   // наружу: '••••3f2a'
  clientId: string | null     // несекретный
  deliveryKopecks: number | null
}
type DeliverySettings = { carriers: { cdek: CarrierSettings; ozon: CarrierSettings }, updatedAt, updatedByActorLoginAt }
```

- `getDeliverySettings()` — для **админки**: возвращает маску/статус, НЕ открытый
  секрет.
- `getRuntimeCredentials(carrier)` — для **рантайма** (`lib/cdek.ts`/`lib/ozon.ts`,
  checkout): расшифровывает и отдаёт `{ clientId, secret, fingerprint }` **только
  если перевозчик `enabled` и полностью настроен**. Для выключенного carrier
  возвращает `undefined`; для включённого, но неполного/повреждённого — бросает
  `DeliveryConfigurationError`. Это путь, которым пользуется витрина.
- `getStoredCredentials(carrier)` — для **проверки связи**: расшифровывает
  сохранённые ключи **независимо от `enabled`** (чтобы протестировать перевозчика
  до включения). Серверный модуль, недоступен из публичных route. Решает пункт
  ревью №1: enabled-gating рантайма не мешает тесту draft/сохранённых ключей.
- `resolveDeliveryMode()` — см. [семантику включения](#семантика-включения-доставки):
  `disabled | pickup_required | error` + список активных перевозчиков. Ошибку
  чтения/расшифровки не глотает — она становится `error` (→503). Включённый, но
  неисправный carrier также делает результат `error`, даже если второй исправен.
- `saveCarrierSettings(carrier, patch, actorLoginAt)` — **атомарно** (одна
  транзакция, `SELECT … FOR UPDATE` singleton-строки): применяет патч к текущей
  строке, вычисляет **итоговое** состояние и проверяет инвариант
  «`enabled ⇒ ключи+тариф`» до коммита. Это решает пункт ревью №5: можно одним
  запросом прислать секрет + тариф + `enabled=true`, и проверяется объединённый
  результат, а не отдельные поля. Шифрует новый секрет (если прислан); пустой/
  отсутствующий секрет старый не затирает.
- `clearCarrierCredentials(carrier, actorLoginAt)` — отдельная атомарная операция:
  под `FOR UPDATE` ставит `enabled=false`, очищает `client_id` и ciphertext, но
  оставляет тариф для последующей повторной настройки. Это единственный способ
  удалить скомпрометированный ключ; пустое поле формы никогда не означает clear.

Все серверные модули, способные расшифровать секрет, начинают с
`import 'server-only'`. DTO для страницы и публичные delivery-модули получают
только нужные данные и не импортируют сырой ciphertext в Client Component.

## Checkout и `createOrder` — единый снимок настроек

`resolveDeliveryMode()` без параметров подходит для отображения checkout и
`/api/checkout/delivery`, но не является достаточной авторизацией создания заказа:
настройки могут измениться между показом формы и оплатой. Внутри `createOrder`
должен использоваться отдельный `getLockedDeliverySnapshot(client)`:

1. после `BEGIN` выполнить `SELECT … FROM store_settings WHERE singleton=true FOR
   SHARE` и на этой строке вычислить mode, active carriers, тариф и fingerprint
   credentials;
2. если mode `error` — бросить `DeliveryUnavailableError` (503); если `disabled` —
   принять заказ без ПВЗ и с `delivery_kopecks=0`; если `pickup_required` —
   проверить, что выбранный carrier остаётся активен;
3. пока совместимая блокировка удерживается, повторно запросить ПВЗ у выбранного
   provider с credentials из этого снимка (таймаут не более 5 секунд), затем
   записать snapshot заказа, тариф и сумму в той же транзакции;
4. `saveCarrierSettings`/`clearCarrierCredentials` используют `FOR UPDATE`, поэтому
   ждут завершения заказа и не могут выключить carrier или заменить тариф между
   проверкой ПВЗ и `INSERT orders`.

Внешний API внутри короткой транзакции здесь допустим: он не имеет побочного
эффекта, защищён таймаутом и защищает от TOCTOU. СДЭК/Ozon provider обязан уметь
принять credentials явным параметром; глобальный cache OAuth-токена по-прежнему
ключуется fingerprint этого снимка. `expectedDeliveryKopecks` сверяется с
зафиксированным тарифом, как и раньше, и при несовпадении даёт `PRICE_CHANGED`.

## Рантайм перевозчиков — `lib/cdek.ts` / `lib/ozon.ts`

Сейчас `credentials()` в `cdek.ts` читает `process.env`. Заменить на
`getRuntimeCredentials('cdek')` (из БД, расшифровка, только для enabled). Поведение
«нет ключей → `unavailable`» сохраняется. Это снимает зависимость от `.env`-секретов
перевозчиков; в `.env` остаётся только `SETTINGS_ENC_KEY` и базовые URL.

**Инвалидация кэша OAuth-токена СДЭК (пункт ревью №4).** Сейчас `tokenCache` в
`cdek.ts` живёт по TTL и не знает о смене ключей — после ротации до истечения TTL
использовался бы токен старого аккаунта. Решение: привязать кэш к **fingerprint**
credentials (например `sha256(clientId + ':' + secret)`, его же отдаёт
`getRuntimeCredentials`). Кэш хранит `{ token, expiresAt, fingerprint }`; перед
использованием сверяем `fingerprint` с текущим — при несовпадении токен
перезапрашивается. Это работает **без межпроцессного сигнала**: каждый воркер
сам обнаружит смену ключа из БД, поэтому ручная инвалидация и `pm2 reload` не
нужны. Тот же приём применим к любому будущему перевозчику с кэшем токена.

## API — `shop/app/api/admin/settings/delivery/route.ts`

Расширить существующий route (iron-session + `assertSameOrigin` уже есть):

- **GET** (`requireAdminApi`): отдаёт `DeliverySettings` со статусами/масками всех
  перевозчиков. Открытый секрет не отдаётся никогда.
- **PATCH** (`requireAdminApi` + `assertSameOrigin`): частичный апдейт одного
  перевозчика — `{ carrier, enabled?, clientId?, secret?, deliveryKopecks? }`.
  Делегирует в `saveCarrierSettings` (атомарная транзакция, проверка **итогового**
  состояния, см. [слой настроек](#слой-настроек--shoplibstore-settingsts)).
  Контракт полей:

  | Поле | Тип / правила |
  |---|---|
  | `carrier` | строго `'cdek' \| 'ozon'`; иначе 400 |
  | `enabled` | boolean; `true` допустимо в том же запросе, что и ключи/тариф |
  | `clientId` | строка после `trim`, 1…256; пустая строка или `null` → 400 (не «не менять») |
  | `secret` | строка после `trim`, 1…512; **отсутствие поля или пустая строка = «не менять»** (старый секрет сохраняется); присланная маска `••••…` отвергается как новое значение |
  | `deliveryKopecks` | `Number.isSafeInteger` и ≥ 0; `null` → 400 |
  | `clearCredentials` | не принимается этим PATCH; используется отдельный endpoint ниже |

  Ключ для `enabled=true` без полного набора (ключи+тариф) → **409** с понятным
  сообщением; неизвестные поля, `undefined` в JSON и неподходящие типы → **400**;
  невалидный JSON → 400. Сервер никогда не добавляет исходное тело запроса к
  сообщению об ошибке или логу.
- **POST `…/clear`** (`requireAdminApi` + `assertSameOrigin`): принимает ровно
  `{ carrier }`, вызывает `clearCarrierCredentials`. Возвращает безопасный
  `DeliverySettings`; включённый carrier в результате всегда `false`. UI называет
  действие «Удалить ключи», требует явного подтверждения и не отправляет секрет.
- **POST `…/test`** «Проверить связь» (`requireAdminApi` + `assertSameOrigin`):
  серверный вызов `listPickupPoints(тестовыйГород)` выбранного перевозчика. Тело
  строгое: `{ carrier, clientId?, secret? }`; неизвестные поля, `null` и неверные
  типы — 400. Контракт:
  - источник ключей: получить сохранённые `getStoredCredentials(carrier)` (даже у
    выключенного), затем наложить все присланные draft `clientId`/`secret`. Значит,
    можно проверить первое подключение и одновременную замену обоих ключей до
    сохранения. Если после наложения нет полного набора — `409 credentials_missing`;
  - provider создаётся с этими credentials явно, не через
    `getRuntimeCredentials()` и не зависит от `enabled`; endpoint не пишет в БД;
  - тестовый город — фиксированный, заведомо существующий (напр. `«Москва»`);
  - **таймаут** запроса к API перевозчика ~5 c; результат усечь (нужен только факт
    связи), возвращать `{ ok: true, sampleCount }`;
  - **безопасные ошибки**: различать `auth_failed` (неверные ключи) / `unavailable`
    (сеть/таймаут) / `ok`, но **без тела ответа перевозчика и без секрета**;
  - rate-limit: максимум 5 попыток за 10 минут по паре `admin loginAt + IP` в общем
    для всех инстансов хранилище (PostgreSQL/Redis; не process-local `Map`);
    превышение → 429 и `Retry-After`. IP берётся только из trusted-proxy chain;
    вызовы не логировать с секретом.

## Безопасность — чек-лист

- [ ] Открытый секрет не уходит в браузер (GET, props, ошибки, логи, `/test`).
- [ ] Секреты шифруются AES-256-GCM с версией формата и AAD `<carrier>:<field>`.
- [ ] `SETTINGS_ENC_KEY` только в `.env`; декодированная длина **ровно 32 байта**.
- [ ] PATCH/POST под `requireAdminApi` + `assertSameOrigin` (CSRF); `/test` с rate-limit.
- [ ] `/test` принимает полные draft credentials и создаёт provider без enabled-gating;
      лимит общий для всех инстансов и возвращает 429/`Retry-After`.
- [ ] Включение перевозчика заблокировано без ключей и тарифа (проверка итогового
      состояния в транзакции, не пополевая).
- [ ] Пустое/отсутствующее поле секрета не затирает сохранённый ключ; маска как
      новое значение отвергается.
- [ ] Ошибка чтения/расшифровки либо любой неисправный enabled-carrier → **503**, а
      не заказ без ПВЗ (`resolveDeliveryMode = error`).
- [ ] `console.error` не печатает тело с секретом.
- [ ] Модули расшифровки помечены `server-only`; удаление credentials выключает
      carrier и очищает ciphertext атомарно.
- [ ] Ротация `SETTINGS_ENC_KEY` выполняется только описанным offline-скриптом с
      backup, `_OLD`, транзакцией и проверкой всех ciphertext.

## Шаги реализации (порядок)

1. `lib/secret-box.ts` (версия+AAD, strict hex/base64) + `SETTINGS_ENC_KEY` в
   `.env.example`; валидация «ровно 32 байта» при старте и `server-only`.
2. Миграция `005_delivery_multi_carrier.sql`: модель заказа, nullable тарифы,
   флаги `DEFAULT false`; обновить `schema.sql`. Затем `006_delivery_carrier_secrets.sql`:
   id, `*_enc`, CHECK `NOT VALID`. Не переиспользовать занятый номер `004`.
3. Backfill/rollout из раздела выше: до нового runtime записать и проверить
   существующие CDEK credentials в БД; после rollout удалить старые env-ключи.
4. `lib/store-settings.ts`: `getDeliverySettings` (маски), `getRuntimeCredentials`
   (enabled-only), `getStoredCredentials` (для теста), `resolveDeliveryMode`,
   `getLockedDeliverySnapshot`, `saveCarrierSettings` и `clearCarrierCredentials`
   (атомарно).
5. `lib/cdek.ts` / `lib/ozon.ts`: ключи из `getRuntimeCredentials`, не из env;
   кэш токена СДЭК привязать к fingerprint credentials.
6. `createOrder` / checkout: перейти на `resolveDeliveryMode` (`disabled` /
   `pickup_required` / `error`→503) вместо `isDeliveryEnabled`; создание заказа
   использует locked snapshot до проверки ПВЗ и `INSERT`.
7. API GET/PATCH, `/clear` и `/test` (draft clientId+secret, таймаут, безопасные
   ошибки, shared rate-limit).
8. `DeliverySettingsForm` — карточки перевозчиков и подтверждённое удаление ключей.
9. Тесты: шифрование round-trip; битый tag/version; **отказ при чужом AAD** (нельзя
   подставить шифртекст другого поля); GET/`/test` не отдают секрет; включение без
   полного набора → 409; атомарный PATCH (секрет+тариф+enabled в одном запросе);
   пустой секрет не затирает; маска как значение отвергается; clear выключает
   carrier и стирает ciphertext; `/test` проверяет полностью draft credentials и
   лимит 429; `resolveDeliveryMode = error`→503 при недоступной БД, расшифровке или
   неисправном enabled-carrier; locked snapshot не допускает смены carrier/тарифа
   между ПВЗ и `INSERT`; смена ключа инвалидирует токен по fingerprint; per-carrier
   тариф; CSRF/anon → 403/401.
10. Реализовать и прогнать offline-ротацию ключа на staging; только затем разрешить
    production-credentials и выполнить `VALIDATE CONSTRAINT`.

## Зависимости и риски

- Зависит от мульти-перевозчик модели из [ozon-pvz.md](ozon-pvz.md) (per-carrier
  тариф/флаги). В связанной спеке номер её миграции должен быть синхронизирован на
  `005_delivery_multi_carrier.sql`; `004` зарезервирован Telegram.
- **Потеря `SETTINGS_ENC_KEY` = потеря всех ключей перевозчиков** (восстановить
  только повторным вводом). Бэкап мастер-ключа хранить отдельно от БД.
- Перенос секретов из `.env` в БД — разовая миграция значений: следовать rollout
  выше, не удалять старые env-ключи до успешного переключения runtime и проверки
  checkout.
- `client_id` формально несекретный, но в UI его тоже стоит не светить лишний раз
  (показывать, но не индексировать/логировать).
