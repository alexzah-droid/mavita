# Админка — усиление модуля управления товарами

Статус: ✅ **реализовано (2026-06-22)**. Дата спецификации: 2026-06-21.

Этот документ фиксирует обязательные исправления по итогам критического ревью
реализации управления товарами. Он дополняет
[admin-products.md](admin-products.md), не меняя его доменную модель,
маршруты или миграцию `002` без явного указания ниже.

Реализация (все пять дефектов + тесты):

- §1 — `lib/admin-product-datetime.ts` (`instantToDateTimeLocal` /
  `dateTimeLocalToInstant`, discriminated `DateTimeResult`), форма
  `AdminProductForm` хранит исходный instant + dirty-флаг каждого поля
  (`lib/admin-product-datetime.test.ts`).
- §2 — `validateProductInput()` принимает только строгий RFC 3339 с offset и
  точностью до минуты; `updateAdminProduct()` проверяет ИТОГОВОЕ состояние после
  `FOR UPDATE`; route мапит `SALE_PRICE_INVALID` и DB CHECK `23514` в один `400`.
- §3 — `PATCH /images` и `DELETE /images/:imageId` возвращают `{ images }`
  (`reorderProductImages` / `deleteProductImage`); форма заменяет локальный список
  ответом, на `409` делает refetch.
- §4 — `DELETE /api/admin/products/:id` принимает `{ confirmationName }`, сверяет
  с `name` без trim в транзакции; «опасная зона» в форме (Архивировать / Удалить
  навсегда).
- §5 — `PRODUCTS_PUBLIC_ORDER_LOCK = 7_903_244_111`, `pg_advisory_xact_lock`
  первым запросом в `createAdminProduct` / `updateAdminProduct` /
  `reorderPublicProducts` / `deleteAdminProduct`.
- Тесты — юниты + `npm run test:integration` (concurrency против реального
  PostgreSQL, `test/products-concurrency.integration.test.ts`) + e2e
  (`e2e/admin-product-photos-archive.spec.ts`).

Правки после ревью (2026-06-22):

- **P0 (cover-инвариант):** все фото-операции (`upload`, `reorderProductImages`,
  `deleteProductImage`) сериализуются на одной строке `products` через
  `SELECT … FOR UPDATE` первым запросом транзакции. Раньше reorder/delete
  блокировали только `product_images`, и гонка delete-последней-обложки против
  upload могла оставить фото без cover. Покрыто integration-тестом.
- **P1 (календарь):** `validateProductInput` проверяет календарную валидность
  компонентов (длина месяца, високосный год, диапазон offset) ДО `toISOString()`:
  `2026-02-30T…Z` больше не нормализуется в март, а отвергается.
- **P1 (реальные flows в concurrency-тесте):** тест вызывает сами
  `reorderPublicProducts`/`updateAdminProduct` с управляемым barrier-хуком
  (`__setLockBarrier`, test-only), а не raw SQL.
- **P1 (gate):** e2e в CI падает (а не skip) без `DATABASE_URL`; `test:integration`
  требует `TEST_DATABASE_URL`. Прогон выполнен на реальном PostgreSQL 16:
  integration 4/4, e2e 4/4.
- **P2 (DST-overlap):** `dateTimeLocalToInstant` возвращает `warning` для
  неоднозначного времени (переход на зимнее время). Overlap определяется по
  ФАКТИЧЕСКОМУ offset до/после перехода в этот день, поэтому ловит и 30-минутные
  откаты (`Australia/Lord_Howe`), а не только часовые. Форма показывает warning
  рядом с полем; e2e проверяет порядок, cover и `409`.
- **P2 (диалог hard delete):** «Удалить навсегда» открывает модальный диалог
  (`role="dialog"`, `aria-modal`) с названием товара и полем подтверждения; поле и
  кнопка «Удалить безвозвратно» вне диалога не показываются, кнопка активна только
  при точном совпадении имени. e2e проходит весь сценарий через диалог.

## Цель и границы

Нужно устранить пять дефектов, которые сейчас приводят к неверному расписанию
скидок, ответу `500` для валидного частичного PATCH, недоступной сортировке фото,
незавершённому сценарию удаления и недетерминированному порядку витрины при
параллельных действиях.

В охвате:

1. дата и время временной скидки;
2. серверная валидация итогового состояния товара;
3. сортировка фотографий в форме редактирования;
4. архивирование и подтверждённое физическое удаление;
5. сериализация операций, меняющих состав или порядок публичной витрины;
6. тесты на каждый сценарий.

Вне охвата: история slug, массовое редактирование, категории, изменение
формата хранения дат или схемы `products`.

## Инварианты

- В БД `sale_starts_at` и `sale_ends_at` остаются абсолютными моментами
  (`TIMESTAMPTZ`); API отдаёт и принимает RFC 3339 с offset/`Z`.
- Поле `datetime-local` всегда показывает **локальное время браузера**, а не
  срез UTC-строки. Повторное открытие и сохранение товара без изменения дат не
  меняет сохранённые моменты времени.
- Любой частичный PATCH либо формирует допустимое итоговое состояние товара,
  либо возвращает контролируемый `400 VALIDATION_ERROR`. Он не должен доходить
  до CHECK-constraint как до обычного пользовательского сценария и не может
  вернуть `500` из-за сочетания новой обычной цены с уже сохранённой скидкой.
- Если у товара есть изображения, у него ровно одна обложка. Порядок и обложка
  меняются одной атомарной операцией.
- Обычное удаление из интерфейса — архивирование (`visibility='hidden'`).
  Физическое удаление возможно только после серверно проверенного подтверждения
  точным текущим названием товара.
- Успешный reorder всегда соответствует полному набору `public`-товаров в
  момент коммита. При изменившемся наборе клиент получает `409`, а не ложный
  `200`.

### Уточнение точности и DST

`datetime-local` в этой форме работает с точностью до минуты (`step="60"`).
Следовательно, пользовательский контракт расписания тоже минутный: сервер
принимает для `sale.startsAt` и `sale.endsAt` только строгий RFC 3339 с `Z` или
числовым offset, у которого секунды и миллисекунды равны нулю. Иначе он отвечает
`400 VALIDATION_ERROR`. Уже сохранённые значения с иной точностью при открытии
формы округлять или молча менять запрещено: форма показывает локальную ошибку
«Время скидки должно быть с точностью до минуты» и не позволяет сохранить
изменения до исправления значения администратором через поддерживаемый путь.

`datetime-local` не содержит timezone и не может однозначно представить
повторяющееся время при переходе на зимнее время. Поэтому форма хранит исходный
ISO-момент каждого поля и признак его изменения: пока поле не менялось, в PATCH
отправляется исходная ISO-строка, а не результат обратного преобразования
отображённой строки. Это сохраняет instant даже в DST-overlap. После изменения
поля `dateTimeLocalToInstant()` использует семантику `new Date(year, month - 1,
day, hour, minute)` текущего браузера; если получившиеся локальные компоненты не
совпадают с введёнными (несуществующее время DST-gap), она возвращает ошибку, а
не нормализованный момент. Для DST-overlap выбран и документирован браузерный
вариант этого конструктора (обычно более ранний offset); рядом с полем показывается
предупреждение о выбранном offset. Функции возвращают discriminated result, а не
бросают исключение:

```ts
type DateTimeResult = { ok: true; value: string } | { ok: false; message: string }
```

Это же правило применяется к preview: при `{ ok: false }` preview показывает
обычную цену и локальную ошибку, не вызывая `toISOString()` у некорректной даты.

## 1. Локальное время расписания скидки

### Поведение формы

В `AdminProductForm` нужны две чистые функции (их можно вынести в
`lib/admin-product-datetime.ts`):

- `instantToDateTimeLocal(iso: string): DateTimeResult` — преобразует RFC 3339
  момент в строку `YYYY-MM-DDTHH:mm` через локальные getter-ы `Date` браузера
  либо возвращает ошибку для невалидного/не-минутного instant;
- `dateTimeLocalToInstant(value: string): DateTimeResult` — интерпретирует
  значение `datetime-local` как локальное время браузера и возвращает
  ISO-момент либо контролируемую ошибку по правилам выше.

Нельзя использовать `new Date(iso).toISOString().slice(0, 16)` для значения
`datetime-local`: это UTC-стена, которую браузер затем интерпретирует как
локальную. Например, `2026-06-21T15:00:00.000Z` в `Europe/Moscow` должен
отобразиться как `2026-06-21T18:00`, а сохранение этого неизменённого значения
должно вернуть исходный `15:00Z`.

Подпись поля остаётся «локальное время», но должна означать именно timezone
браузера. Пустое значение по-прежнему отправляется как `null`. Некорректное
значение не должно вызывать исключение при рендере preview: форма показывает
обычную цену и выводит локальную ошибку/получает `400` после submit.

### Приёмка

- В timezone `Europe/Moscow` редактирование товара со стартом `15:00Z` показывает
  `18:00`; сохранение без правок сохраняет тот же instant.
- Такой же round-trip покрыт как минимум ещё одним timezone с отличным от UTC
  смещением.
- `startsAt=null` и `endsAt=null` не меняются при сохранении остальных полей.
- Значение с секундами или миллисекундами отвергается сервером; форма не меняет
  такой ранее сохранённый instant молча.
- Для DST-overlap сохранение неизменённого поля отправляет исходный instant; для
  DST-gap редактирование возвращает локальную ошибку и не отправляет PATCH.

## 2. Частичный PATCH цены и скидки

`validateProductInput()` продолжает проверять форму входного body. Проверка
зависимого ограничения должна выполняться после чтения заблокированной строки в
`updateAdminProduct()` по **итоговому** состоянию:

```text
finalPrice = input.priceKopecks ?? current.price_kopecks
finalSale  = input.sale === undefined ? current sale : input.sale

finalSale === null || finalSale.priceKopecks < finalPrice
```

Тем самым должны работать все варианты:

| PATCH | Текущая скидка | Результат |
| --- | --- | --- |
| `{ priceKopecks: 5000 }` | `7500` | `400 VALIDATION_ERROR`, запись не меняется |
| `{ priceKopecks: 5000, sale: null }` | `7500` | `200`, цена меняется, скидка очищается |
| `{ priceKopecks: 8000 }` | `7500` | `200` |
| `{ sale: { … } }` | любая | проверяется относительно текущей цены |

DB CHECK `products_sale_below_price` остаётся защитой целостности. Route handler
всё равно обязан безопасно преобразовать ожидаемое нарушение `23514` в тот же
контрактный `400`, не раскрывая детали PostgreSQL.

`validateProductInput()` обязан проверять именно строгий RFC 3339: timezone
обязателен (`Z` или `±HH:MM`), строка без offset, date-only и дата, которую
`Date` лишь эвристически распознаёт, невалидны. После чтения `FOR UPDATE`
`updateAdminProduct()` строит также итоговое окно скидки; существующее окно
можно использовать без повторной валидации, потому что его уже гарантирует DB
CHECK, но новое `input.sale` валидируется полностью до UPDATE. При любой ошибке
итогового состояния UPDATE не выполняется.

## 3. Сортировка фотографий

В блоке «Фото» формы редактирования добавить drag-and-drop (или доступные кнопки
«влево/вправо») для порядка всех изображений. После успешной перестановки клиент
посылает полный актуальный набор:

```ts
PATCH /api/admin/products/:id/images
{ orderedImageIds: number[], coverImageId: number }
```

Текущая обложка сохраняется при перестановке. Назначение обложки использует тот
же запрос; нельзя создавать отдельный flow, который не передаёт полный порядок.
На `409` форма повторно загружает товар и показывает сообщение «Список фото
изменился в другом окне — повторите действие». На сетевую/серверную ошибку
локальный optimistic-порядок откатывается либо обновляется данными сервера.

После удаления текущей cover UI обязан сразу отразить cover, назначенную сервером
следующей по `sortOrder`; для этого DELETE-ответ возвращает обновлённый список
изображений или клиент делает явный refetch до следующего действия.

Выбранный контракт: успешные `PATCH /images` и `DELETE /images/:imageId`
возвращают `{ images: AdminImage[] }`, где список отсортирован по
`sortOrder, id` и содержит ровно актуальный `isCover`. Форма заменяет локальный
список этим ответом. Это исключает следующее действие на устаревшей cover; при
`409` она делает GET товара, заменяет список и показывает указанное сообщение.

## 4. Архивирование и физическое удаление

### Интерфейс

В форме редактирования нужна «опасная зона»:

- основное действие «Архивировать» выставляет `visibility='hidden'` через PATCH
  и не удаляет данные;
- «Удалить навсегда» открывает диалог с названием товара и полем
  подтверждения; кнопка доступна только когда введённая строка в точности равна
  текущему `product.name`;
- до подтверждения не должно выполняться DELETE.

### API

`DELETE /api/admin/products/:id` принимает JSON body
`{ confirmationName: string }`. В одной транзакции сервер блокирует строку,
сверяет `confirmationName` с текущим `name`, затем удаляет товар. Несовпадение —
`400 VALIDATION_ERROR`; отсутствующий товар — `404`. Клиентская проверка лишь UX,
серверная обязательна.

`confirmationName` обязателен, имеет тип string и сравнивается с `name` без
trim, нормализации или case-folding. Некорректный/пустой JSON и отсутствие поля
также дают `400 VALIDATION_ERROR` до удаления. Если товар был `public`, DELETE
берёт блокировку порядка витрины из следующего раздела до `SELECT ... FOR UPDATE`
и остаётся в ней до commit. Успех возвращает `{ ok: true }`.

Остаются существующие гарантии: `order_items.product_id` получает `NULL` по FK,
а файл изображений становится orphan и подлежит штатному cleanup job.

## 5. Конкурентная сортировка витрины

Обычный `SELECT … WHERE visibility='public' FOR UPDATE` не блокирует
непубличную строку, которую другой запрос может опубликовать после проверки
набора. Для операций, способных изменить состав или порядок публичной витрины,
нужна единая транзакционная advisory-блокировка PostgreSQL.

Ввести один документированный ключ `PRODUCTS_PUBLIC_ORDER_LOCK = 7_903_244_111`
типа signed `bigint`. Единственный допустимый способ захвата —

```sql
SELECT pg_advisory_xact_lock($1::bigint)
```

с этим параметром внутри уже открытой `withTransaction`. Блокировка должна быть
первым SQL-запросом транзакции, до чтения товара, списка `public` или вычисления
`max(sort_order)`. Строка `products:public-order` — только человекочитаемое имя
этого ключа, не параметр SQL. Брать блокировку нужно в следующих flows:

1. `POST /api/admin/products`;
2. `PATCH /api/admin/products/:id`;
3. `POST /api/admin/products/reorder`.
4. `DELETE /api/admin/products/:id`.

Допустимо брать эту короткую блокировку для каждого product PATCH — это проще и
исключает обратный порядок блокировок. После её получения reorder читает полный
набор public ID, сверяет его с body и либо записывает `10, 20, …`, либо отвечает
`409`. Создание/публикация в том же протоколе назначает `max(sort_order)+10`.

Для простоты и исключения гонки «прочитать visibility → решить, нужен ли lock»
реализация берёт эту блокировку для **каждого** `POST`, `PATCH` и `DELETE` товара,
а также для reorder. После захвата PATCH/DELETE читает целевую строку через
`FOR UPDATE`; только затем проверяет переход visibility или подтверждение имени.
Другие SQL-пути, миграции и ручные операции не должны менять `visibility` или
`sort_order` в обход этого протокола; если такой путь появится, он обязан взять
тот же ключ. Уровень изоляции остаётся `READ COMMITTED`: корректность обеспечена
единым transaction-scoped advisory lock и `FOR UPDATE` строк.

## Тесты и readiness

Добавить тесты к существующим suite:

- unit для конвертации local datetime ↔ instant, включая `Europe/Moscow` и
  round-trip без изменения значения;
- `updateAdminProduct` и route test для частичного PATCH обычной цены при
  существующей скидке: `400`, без UPDATE и без `500`;
- компонентный/e2e-тест сортировки фото, сохранения cover и обработки `409`;
- API-тест hard delete: неверное/отсутствующее `confirmationName` не удаляет
  строку, точное название удаляет; e2e-тест архивирования;
- интеграционный concurrency-тест: reorder параллельно с публикацией товара
  сериализуется, и устаревший reorder получает `409`.

### Интеграционный контур тестов

Указанный concurrency-тест нельзя заменять mock-тестом `withTransaction` или
проверкой текста SQL: он запускается против реального PostgreSQL. Добавить
отдельную команду `npm run test:integration`, которая требует
`TEST_DATABASE_URL`, создаёт уникальную schema/database на запуск, применяет
`sql/schema.sql` и удаляет её в `finally`. В CI PostgreSQL предоставляется service
container; локальный запуск описывается в README/operations. Набор запускается
последовательно либо каждая проверка использует отдельную schema, чтобы advisory
key не создавал межтестовых гонок.

Concurrency-тест открывает два независимых pool/client и управляемый барьер:
первый reorder удерживает lock после его захвата, второй PATCH публикует товар с
устаревшим списком ID, затем барьер освобождается. Ожидаемые результаты: reorder
commitится только для точного набора, ожидающий PATCH публикует товар после него;
повторный reorder со старым набором получает `409`. Отдельно покрыть hard delete
`public`-товара в том же протоколе.

E2E для архивирования и фото получает явную DB-fixture и авторизованную сессию;
не допускается опираться на seed/fallback без `DATABASE_URL`. В release gate
добавить интеграционный и e2e-наборы:

```sh
npm run typecheck && npm test && npm run test:integration && npm run build && npm run test:e2e
```

Готовность к релизу: выполнить gate выше, затем ручной smoke-test с реальным
часовым поясом администратора, DST-сценарием (если применимо) и двумя вкладками
админки.
