# Ozon Доставка — технический каталог и остатки FBS

Статус: **спецификация обновлена под подход «загрузка по API + ручное скрытие в ЛК»; на ревью владельца; реализация — только после ревью и Gate-0 ручного скрытия.** Живым ключом подтверждён import карточки; отдельный smoke записи FBS-остатка обязателен до включения live-sync. Автоматическое скрытие через `visibility/set` НЕ используется (метод залочен программой «Ozon Логистика и Select», недоступной без истории продаж на маркетплейсе). Доступность ручного скрытия в ЛК при текущем статусе аккаунта пока не подтверждена и является жёстким внешним gate этой фазы. См. «Пересмотр подхода (2026-06-22)».
Дата: 2026-06-21; обновлено 2026-06-22.  
Зависит от: [выбор ПВЗ Ozon](done/ozon-pvz.md), [настройки перевозчиков](done/admin-delivery-settings.md), [админка товаров](done/admin-products.md).

## Контекст и цель

МАВИТА продаёт товары только через собственный сайт и хранит их только на
собственном складе. Ozon используется как логистический партнёр по модели
**FBS + Ozon Доставка**: после оплаты на сайте посылка должна быть передана в
Ozon и выдана в ПВЗ либо доставлена получателю.

Для Ozon Доставки необходим технический каталог товаров в Seller API. Он нужен
для идентификации позиции, габаритов, веса, маркировки, цены и остатка.

Идеальная цель — держать карточки **скрытыми** с витрины Ozon (продаём только со
своего сайта). Но API-механизм скрытия (`visibility/set`) залочен программой
«Ozon Логистика и Select», недоступной МАВИТЕ без истории продаж на маркетплейсе.
Поэтому в этой фазе **приложение не скрывает карточки само** — оно лишь грузит и
актуализирует их по API, а **скрытие выполняет оператор вручную в ЛК** после
загрузки — только если Gate-0 подтвердит, что эта операция доступна текущему
аккаунту (см. «Пересмотр подхода»). Это осознанный компромисс с известным
ограничением: между загрузкой и ручным скрытием карточка публична на витрине Ozon,
но приложение держит на ней **нулевой FBS-остаток**. Ненулевой остаток разрешён
только после ручного скрытия и его подтверждения в админке.

Цель этой фазы — дать оператору управляемую синхронизацию выбранных товаров и их
FBS-остатков из МАВИТА в Ozon (по кнопке и по расписанию, со статусом в админке),
подготовив связку для следующей фазы — создания заказа Ozon после оплаты на сайте.

## Пересмотр подхода (2026-06-22)

Исходная спека требовала, чтобы приложение само держало карточку непубличной
через `visibility/set`. Живой тест показал: метод существует и доступен ключу
(`200`), но возвращает `seller_is_not_connected_to_ozon_logistics_and_select` —
программа «Ozon Логистика и Select», дающая скрытие, **недоступна** без истории
FBS/FBO-продаж на маркетплейсе. Подключение — внешний бизнес-гейт, не код.

Решение владельца: **не ждать разблокировки, а реализовать управляемую загрузку
по API; скрытие делать вручную в ЛК.** Конкретно:

1. Приложение реализует синхронизацию каталога и FBS-остатка МАВИТА → Ozon
   (import/update/stock), **но не вызывает `visibility/set`** (метод залочен).
2. **Заливку/обновление карточек инициирует оператор кнопкой** в админке —
   приложение не публикует ничего само и не по расписанию (контроль момента
   публикации остаётся за человеком).
3. После успешного import приложение фиксирует `awaiting_moderation` и держит
   FBS-остаток `0`. Оператор дожидается модерации, вручную скрывает карточку в ЛК
   (бейдж «Ozon Доставка») и подтверждает это действие в админке.
4. **Принятое ограничение:** до ручного скрытия карточка публична на витрине,
   но с нулевым остатком и не должна принимать FBS-заказы. После аудируемого
   подтверждения скрытия оператор отдельной кнопкой выставляет нужный остаток.
   Продаваемое окно с ненулевым остатком не допускается: эта фаза не создаёт и не
   учитывает прямые заказы с витрины Ozon.
5. По расписанию допускается только **обновление FBS-остатка** уже загруженных
   карточек с подтверждённым ручным скрытием — оно не меняет видимость. Полный
   re-import контента — только по кнопке оператора; он сбрасывает подтверждение
   скрытия и возвращает остаток в `0` до повторной проверки в ЛК. Отдельно
   разрешён только read-only polling модерации: он не импортирует контент и не
   меняет остаток или видимость.
6. Модерация — асинхронный внешний этап: приложение не ждёт её в import worker,
   а выполняет отдельный read-only polling статуса. Пока Ozon не вернул
   `MODERATED`, ненулевой остаток невозможен.
7. **Gate-0 до реализации:** оператор вручную проверяет в ЛК на существующей
   тестовой карточке, что при текущем аккаунте доступно действие скрытия с
   витрины и оно реально даёт бейдж/состояние «Ozon Доставка». Если ЛК требует
   те же продажи/подключение, что и `visibility/set`, ручной процесс невалиден:
   реализация live-sync не начинается, а владелец отдельно выбирает публичную
   торговлю ради онбординга либо парковку/отказ от интеграции.

Когда/если программа «Ozon Логистика и Select» станет доступна, скрытие можно
будет автоматизировать через `visibility/set` (контракт уже вскрыт, см. discovery) —
это отдельное улучшение, не блокирует текущую фазу.

## Границы фазы

### Входит

- технические карточки выбранных товаров в Ozon (загрузка/обновление по API);
- выбор существующего FBS-склада Ozon;
- синхронизация цены, изображений и FBS-остатка на этом складе;
- админские данные товара, валидация, **ручной (по кнопке) запуск загрузки** и
  **фоновое обновление только остатка**;
- UI в админке (Доставка → Ozon): элементы управления загрузкой/актуализацией
  товаров и статус синхронизации ПВЗ, с видимым статусом и деталями (см. ниже);
- аудит результата и понятные ошибки для оператора;
- жёсткий feature gate, не позволяющий показать Ozon на checkout до следующей
  фазы.

### Не входит

- **автоматическое скрытие карточки через `visibility/set`** (метод залочен
  программой; скрытие — ручной шаг оператора в ЛК);
- создание, подтверждение, отмена и отслеживание отправлений Ozon;
- печать этикеток, возвраты, маркировка отправления;
- расчёт реального тарифа Ozon на checkout;
- FBO, хранение товара на складах Ozon;
- автоматическая публикация/скрытие по расписанию (по расписанию — только остаток);
- двусторонняя синхронизация: Ozon не является источником правды для цены,
  описания, фотографий и остатков;
- автоматическое создание склада, категорий или карточек для всех товаров
  без явного выбора оператора.

## Решения и инварианты

| Вопрос | Решение |
|---|---|
| Схема логистики | Только FBS: товар остаётся на складе МАВИТА. |
| Источник правды | БД МАВИТА. Ozon получает только явно разрешённые данные. |
| Набор товаров | Content-import получает только `enabled=true`. Ранее импортированный отключённый профиль может попасть лишь в `zero_stock`, чтобы убрать доступный остаток; новый товар в Ozon при отключении не создаётся. |
| Витрина Ozon | Приложение **не управляет видимостью** (метод `visibility/set` залочен программой). Скрытие — **ручная операция оператора в ЛК** после import и модерации; до её подтверждения приложение держит FBS-остаток `0`. `visibility/set` оставлен для будущего, когда программа откроется. |
| Кто инициирует загрузку | Только оператор кнопкой в админке. Приложение не публикует карточки само и не по расписанию. По расписанию — только обновление FBS-остатка карточек с подтверждённым ручным скрытием и read-only polling модерации. |
| Идентификатор позиции | Неизменяемый `offer_id = mavita-<product.id>`. Изменение `slug` не создаёт новую карточку Ozon. |
| FBS-лимит | `ozon_product_profiles.fbs_stock_quantity` — независимый целый лимит для выбранного FBS-склада. Он не меняет `products.in_stock`, витрину и checkout сайта. |
| Цена | Текущая эффективная цена сайта (активная цена по акции либо обычная), в рублях с двумя знаками, без вычислений через `float`. |
| Удаление | Синхронизация не удаляет удалённые/отключённые позиции в Ozon. Для отключённой позиции ставится остаток `0`. |
| Включение доставки | До реализации следующей фазы Ozon не показывается покупателю даже при свежем каталоге ПВЗ и заданных ключах. |

## Обязательный discovery gate

До написания HTTP-клиента исполнитель обязан сверить актуальную официальную
документацию Seller API и записать реальные версии методов в код/документацию.
Проверить необходимо:

1. нужен ли Seller API product catalog именно для отправления стороннего магазина
   через Ozon Доставку; если нет — пересмотреть эту фазу, а не заводить карточки
   без необходимости;
2. импорт/обновление карточки и проверку статуса асинхронного импорта;
3. дерево категорий, обязательные характеристики и допустимые значения;
4. передачу изображений по URL;
5. выбор FBS-склада и установку FBS-лимита;
6. создание непубличной карточки специально для Ozon Доставки;
7. точные роли API-ключа для каждого вызова;
8. endpoint/поле product-info для статуса модерации и, отдельно, для читаемого
   признака скрытия карточки («Ozon Доставка»/не на витрине).
9. **Gate-0:** ручное скрытие в ЛК доступно текущему аккаунту без подключения к
   «Ozon Логистика и Select». Зафиксировать действие, итоговый бейдж/статус и
   при недоступности остановить live-процесс до решения владельца.

> **Обновление 2026-06-22 (см. «Пересмотр подхода»):** требование «приложение
> обязано скрыть карточку через API, иначе стоп» снято. API-скрытие залочено
> программой, поэтому скрытие — ручной шаг оператора в ЛК, а discovery ниже
> сохранён как фактический результат живых проверок. Пункт 6 (непубличная
> карточка через API) — будущее улучшение, не блокер этой фазы.

> **Гейт подтверждения скрытия:** до первого включения ненулевого FBS-остатка
> выполнить read-only discovery product-info. Если Ozon возвращает надёжный
> признак скрытия, `stock-update` обязан проверять его сервером непосредственно
> перед отправкой ненулевого остатка. Если признака нет, это явно фиксируется в коде и UI как
> подтверждение оператора (honor-system), а не как верификация Ozon; событие всё
> равно аудируется. Нельзя выдавать такой путь за автоматическую проверку.

### Результат discovery от 2026-06-21

Проверка выполнена на production отдельным ключом с ролями `Product`,
`Description Category`, `Warehouse`. Ключ, `Client-Id` и полные ответы API не
сохранялись в документации или логах.

| Проверка | Результат | Решение для реализации |
|---|---|---|
| Склады | `POST /v1/warehouse/list` отключён: `400`, code `9`, `obsolete method cannot be used`. `POST /v2/warehouse/list` доступен и возвращает `{ warehouses, has_next, cursor }`. После настройки в ЛК возвращается один склад типа `fbs` со статусом `created`, first-mile `DROP_OFF` и назначенным timeslot. | Использовать только `/v2/warehouse/list` с cursor-pagination. Склад существует; его id можно выбирать после реализации admin endpoint. |
| Методы доставки | `POST /v2/delivery-method/list` с FBS-складом отвечает `200`, но возвращает пустой `delivery_methods`. | Не использовать этот endpoint как readiness-проверку FBS: он предназначен для realFBS. Пригодность FBS/Ozon Доставки подтверждается контролируемым product/order smoke следующей фазы. |
| Категории | `POST /v1/description-category/tree` доступен. Leaf содержит `type_id` внутри родительского `description_category_id`; доступно 8 403 leaf-type, найдено 19 типов со словом «свеча». | В профиле и UI хранить обязательную пару `description_category_id` + `type_id`, а не один `category_id`. |
| Атрибуты | `POST /v1/description-category/attribute` и `/v1/description-category/attribute/values` доступны. В ответе атрибута используется `attribute_complex_id`. | Валидировать атрибуты по обоим id категории; точный JSON для product-import фиксируется только после разрешённого smoke-import. |
| Product read-only | `POST /v3/product/list` и `/v4/product/info/limit` доступны; старый `/v2/product/info/limit` возвращает `404`. | Не использовать версии методов из старых статей без живой проверки. |
| Статус модерации и скрытия | До реализации polling выполнить read-only probe актуального product-info. Кандидат по текущей документации: `POST /v3/product/info/list`, поле `statuses.moderate_status`; в live-дампе `mavita-9` читаемого признака скрытия пока не зафиксировано. | Зафиксировать реальный endpoint/поле статуса модерации. Отдельно зафиксировать, доступен ли надёжный признак скрытия: при наличии использовать его перед ненулевым stock, при отсутствии включить явно обозначенный honor-system. |
| Import и непубличность | Контролируемый import `mavita-9` принят Ozon (`200`) без штрихкода и без отправки stock; Ozon создал `product_id=5189655669` и штрихкод автоматически. Карточка сразу получила `VISIBLE` + `MODERATED`, хотя stock равен нулю. `POST /v1/product/archive` вернул `result=true`; после него карточка `INVISIBLE`. | Нулевой stock **не** является механизмом скрытия. Archive обратим, но не позволяет держать синхронизируемый FBS-остаток. Механизм скрытия найден отдельно — см. строку «Скрытие с витрины» ниже; `archive` как fallback больше не нужен. |
| Скрытие с витрины (root cause) | `POST /v1/product/visibility/set` существует и доступен текущим ключом (`200`, не `403` — роль есть). Тело: `{ item_placement: [{ sku, placement: <enum 1\|2\|3, 0 запрещён> }] }` (по `sku`, не `product_id`). Но метод вернул пер-товарную ошибку `items_errors:[{code:"seller_is_not_connected_to_ozon_logistics_and_select"}]`: аккаунт МАВИТА **не подключён к программе «Ozon Логистика и Select»**, которая и даёт API-скрытие. | `visibility/set` — будущий официальный механизм автоматизации, совместимый с FBS-остатком после онбординга. Ручной путь не предполагается доступным без проверки: Gate-0 обязан подтвердить его отдельно; при недоступности это release-blocker текущей фазы. |
| Статус импорта и stock write | Stock write не проверялся отдельно. | Выполнить контролируемый smoke по текущему ручному сценарию под `OZON_CATALOG_SYNC_ENABLED`: import с `0`, polling модерации, ручное скрытие, затем stock write. Подключение к программе не требуется, пока приложение не вызывает `visibility/set`. |

Минимальные роли подтверждены для read-only методов. Механизм автоматического
скрытия технической карточки подтверждён официально (`visibility/set`, см. строку
выше), но это будущая ветка. Release-gates текущей фазы — Gate-0 доступности
ручного скрытия, успешный controlled smoke import/stock, polling модерации и
явное решение по API-верификации скрытия либо honor-system. Пока Gate-0 не
пройден, нельзя предполагать, что онбординг в «Ozon Логистика и Select» не
блокирует ручный процесс.

### Doc-research к контролируемому smoke (2026-06-21)

Дополнение к таблице выше по пунктам, которые live-прогон не трогал (они создают
карточку либо меняют состояние Ozon): import, непубличность, статус импорта,
остатки. Данные собраны из **вторичных** источников — официальные страницы
`dev.ozon.ru`/`seller.ozon.ru` отдают redirect-петлю автоматическому фетчу,
поэтому версии и контракты ниже это **кандидаты для smoke, а не подтверждённый
факт**; финализировать только живым ключом и официальной страницей метода.

- **Непубличная карточка (будущее улучшение) — кандидат найден:**
  `POST /v1/product/visibility/set` — **beta-метод, добавлен 2026-04-06**,
  управляет видимостью товара на витрине Ozon/Ozon Select, позволяет скрыть
  отдельные карточки (новые и старые, с остатком и без), оставив их в ЛК. Это
  ровно искомый механизм «карточка в ЛК, но не на витрине». Подтверждён вторично
  двумя независимыми запросами; **обязательна финальная сверка официальной
  страницей метода + ответом API в smoke.** Риски: (а) beta — контракт может
  меняться; (б) роль метода может не входить в текущий
  `Product`/`Description Category`/`Warehouse` — при `403` зафиксировать
  недостающую роль, не повышать до `Admin`.
- **Импорт карточки:** кандидат `POST /v3/product/import` (не v2 — согласуется с
  тем, что на проде read-методы уже `v3`/`v4`, а `v2/product/info/limit` даёт
  `404`). Тело: `offer_id`, пара `description_category_id`+`type_id`, атрибуты,
  `images` (публичные URL), `primary_image`, габариты/вес.
- **Статус асинхронного импорта:** `POST /v1/product/import/info` по `task_id`
  → `items[]` с `offer_id`, `product_id`, `status`. Импорт не считать успешным до
  подтверждённого статуса и получения `product_id` (как и требует алгоритм спеки).
- **Остатки FBS:** `POST /v2/products/stocks` с `warehouse_id` из
  `/v2/warehouse/list`. Ставить остаток только после успешного импорта; для
  disabled/нулевого — `0`.
- **Изображения:** URL-ами в `images` при импорте; публичный HTTPS без авторизации
  обеспечивается нашим `NEXT_PUBLIC_BASE_URL`.

Вывод doc-research **обновлён 2026-06-22**: `v1/product/visibility/set` —
подтверждённый официальный механизм скрытия (см. строку «Скрытие с витрины» в
таблице discovery и official-quote ниже), совместимый с обновлением FBS-остатка.
Он **не** снят с бета-статуса и недоступен аккаунту до подключения к программе,
поэтому не входит в текущий ручной процесс и не является его release-blocker.

### Официальное подтверждение механизма скрытия (2026-06-22)

Официальная справка Ozon «Как скрыть товар с витрин Ozon и Селект»
подтверждает все ключевые инварианты фазы:

- скрытие выполняется методом `/v1/product/visibility/set` — ровно для кейса
  «продавать только со своих площадок» (= кейс МАВИТА);
- скрыть можно **после создания и прохождения модерации** карточки (тестовая
  `mavita-9` уже `MODERATED`);
- скрытые позиции получают бейдж **«Ozon Доставка»** и фильтр
  *Признаки товара → Ozon Доставка* — визуальная проверка скрытия без API;
- скрытые товары можно поставлять на FBO, **обновлять остатки на FBS** и
  отгружать для заказов с других площадок → скрытие **совместимо** с
  поддержанием синхронизируемого FBS-остатка (то, чего не давал `archive`).

Справка описывает поведение для **уже подключённого** продавца и не упоминает
предусловие подключения к программе, на которое наткнулся живой вызов. Поэтому
онбординг и подбор `placement` (1/2/3) остаются отдельным будущим улучшением;
текущая фаза использует ручное скрытие, не вызывает `visibility/set` и не ждёт
этого подключения.

Источники (вторичные): Ozon for dev 446/448 (Ozon Логистика), `docs.ozon.ru/api/seller`,
`api-seller.ozon.ru/apiref`, seller.ozon.ru media «Новые возможности Ozon Доставки»
(анонс `v1/product/visibility/set`), client-библиотеки gam6itko/diphantxm как кросс-сверка.

## Доступы и секреты

Для unit-тестов и разработки ключ не нужен: HTTP вызовы должны быть полностью
замокированы. Для интеграционной проверки нужен **новый отдельный** ключ,
который не используется для существующего каталога ПВЗ.

Первичный минимальный набор ролей при выпуске ключа:

- `Product` — read-only доступ подтверждён; право на импорт/обновление карточек и остатков проверяется только разрешённым smoke;
- `Description Category` — категории и атрибуты;
- `Warehouse` — чтение доступных складов.

`Admin` и `Admin read only` для этой фазы запрещены. Если Ozon вернёт `403`,
исполнитель обязан зафиксировать endpoint и недостающую роль, а не повышать
права до Admin. Роль `Barcode` не нужна, пока Ozon создаёт штрихкод при import;
отдельно добавлять её можно только при необходимости управлять штрихкодами через
API.

`Client-Id` и `Api-Key` сохраняются существующим механизмом шифрования
`store_settings` (`ozon_client_id`, `ozon_api_key_enc`). Они никогда не
возвращаются в браузер, не выводятся в логи и не попадают в командную строку.

## Модель данных

Нужны две миграции после существующей `009_ozon_catalog_sync.sql`. Схема профиля
не зависит от контрактов import и может быть подготовлена заранее; включать
live-sync нельзя до контролируемого smoke записи FBS-лимита и подтверждения
актуальной wire-формы import.

### `010_ozon_fbs_catalog.sql`

```sql
CREATE TABLE ozon_product_profiles (
  product_id              INTEGER PRIMARY KEY REFERENCES products(id) ON DELETE CASCADE,
  enabled                 BOOLEAN NOT NULL DEFAULT false,
  offer_id                TEXT NOT NULL UNIQUE,
  fbs_stock_quantity      INTEGER NOT NULL DEFAULT 0
                            CHECK (fbs_stock_quantity >= 0),
  description_category_id BIGINT,
  type_id                 BIGINT,
  barcode                 TEXT,
  weight_grams            INTEGER,
  length_mm               INTEGER,
  width_mm                INTEGER,
  height_mm               INTEGER,
  attributes_json         JSONB NOT NULL DEFAULT '[]'::jsonb,
  ozon_product_id         BIGINT,
  import_task_id          TEXT,
  remote_state            TEXT NOT NULL DEFAULT 'not_synced'
                           CHECK (remote_state IN ('not_synced','pending','awaiting_moderation','awaiting_manual_hide','hidden_confirmed','invalid','failed','disabled')),
  content_synced_at       TIMESTAMPTZ,
  stock_synced_at         TIMESTAMPTZ,
  moderation_started_at   TIMESTAMPTZ,
  last_moderation_checked_at TIMESTAMPTZ,
  moderation_status       TEXT,
  manual_hidden_confirmed_at TIMESTAMPTZ,
  manual_hidden_confirmed_by_login_at BIGINT,
  hidden_verified_at      TIMESTAMPTZ,
  hidden_verification_method TEXT
                           CHECK (hidden_verification_method IN ('api','operator')),
  content_dirty           BOOLEAN NOT NULL DEFAULT true,
  stock_dirty             BOOLEAN NOT NULL DEFAULT true,
  last_stock_sent_quantity INTEGER NOT NULL DEFAULT 0
                           CHECK (last_stock_sent_quantity >= 0),
  compliance_status       TEXT NOT NULL DEFAULT 'not_checked'
                           CHECK (compliance_status IN ('not_checked','ready','blocked')),
  compliance_note         TEXT,
  last_error_code         TEXT,
  last_error_message      TEXT,
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT ozon_profile_dimensions_positive CHECK (
    (weight_grams IS NULL OR weight_grams > 0) AND
    (length_mm IS NULL OR length_mm > 0) AND
    (width_mm IS NULL OR width_mm > 0) AND
    (height_mm IS NULL OR height_mm > 0)
  ),
  CONSTRAINT ozon_profile_category_pair CHECK (
    (description_category_id IS NULL) = (type_id IS NULL)
  )
);

ALTER TABLE store_settings
  ADD COLUMN IF NOT EXISTS ozon_fbs_warehouse_id BIGINT,
  ADD COLUMN IF NOT EXISTS ozon_fbs_warehouse_name TEXT;
```

`offer_id` создаётся только сервером по шаблону `mavita-<product_id>` при
создании profile и больше не редактируется. `description_category_id` и
`type_id` — обязательная пара leaf-типа из `/v1/description-category/tree`.
`fbs_stock_quantity` — лимит исключительно на стороне выбранного FBS-склада:
новый профиль начинает с `0`; его изменение не трогает `products.in_stock` и
доступность товара на сайте. Полноценный складской учёт сайта остаётся отдельным
будущим решением.
`import_task_id` хранится строкой до живого подтверждения его типа в актуальном
контракте Ozon. `attributes_json` хранит нормализованный массив с локальным
`attributeComplexId`, который при обращении к Ozon сопоставляется с
`attribute_complex_id`. Точная wire-форма значений фиксируется после
разрешённого smoke-import; произвольный JSON из браузера не принимается без
серверной валидации по обоим id категории.

Добавить `updated_at` trigger, аналогичный `products_set_updated_at`, индексы
на `(enabled, remote_state)` и `ozon_product_id`, а также partial unique index
на `barcode WHERE barcode IS NOT NULL`.

Любое изменение импортируемого контента сбрасывает
`manual_hidden_confirmed_at/manual_hidden_confirmed_by_login_at`,
`hidden_verified_at/hidden_verification_method` и ставит `content_dirty=true`,
`stock_dirty=true`. Перед следующим content-import worker сначала обязан
отправить остаток `0`, а затем выполнить import; до повторного скрытия в ЛК
ненулевой остаток не восстанавливается. `last_stock_sent_quantity` — последнее
успешно принятое Ozon значение, а не источник правды склада. `remote_state` описывает жизненный этап карточки, а
`content_dirty`/`stock_dirty` — отставание соответствующей синхронизации; они не
подменяют друг друга. `moderation_started_at` задаёт дедлайн polling: если
карточка не достигла конечного статуса за `OZON_MODERATION_MAX_AGE_HOURS` (по
умолчанию 168), worker переводит её в `failed` и создаёт alert оператору.
`compliance_status='ready'` означает, что оператор проверил требования Ozon к
категории (включая сертификат/декларацию, если требуется) и внёс нужные сведения
в ЛК. `blocked` ставится при известном препятствии к модерации (нет требуемого
документа, он отклонён либо категория не допускается); и `blocked`, и
`not_checked` одинаково блокируют import. Файлы документов в приложении не
хранятся.

### `011_ozon_catalog_product_sync_runs.sql`

Массовая и single-item синхронизация требуют персистентной очереди, а не только
поля на profile. Нужны:

- `ozon_catalog_product_sync_runs`: UUID run id, `kind` (`single`/`bulk`),
  `operation` (`content_import`/`stock_update`/`zero_stock`/`moderation_poll`), snapshot
  `warehouse_id`, `status` (`queued`/`running`/`completed`/`failed`), actor,
  счётчики, безопасный summary, `lease_token`, `lease_expires_at`, timestamps;
- `ozon_catalog_product_sync_run_items`: `(run_id, product_id)` unique,
  snapshot `products.updated_at`/`profile.updated_at`, desired stock, status,
  attempts и безопасная ошибка.

Worker захватывает только просроченный или свободный lease и сверяет token при
каждой записи. Фоновый `moderation_poll` читает только профили
`awaiting_moderation` и не меняет каталог, видимость или остаток. Фоновый
`stock_update` выбирает только `hidden_confirmed` профили с `stock_dirty=true`
и непустым `manual_hidden_confirmed_at`; `zero_stock` также обязан выбрать
`disabled` профили с `ozon_product_id IS NOT NULL` и (`stock_dirty=true` или
`last_stock_sent_quantity > 0`). Для них отправляется stock `0`, даже если они
больше не `enabled`; только после успеха записываются
`last_stock_sent_quantity=0` и `stock_dirty=false`.

Перед **каждым** HTTP-вызовом worker повторно читает profile под row-lock и
сверяет `lease_token`, snapshot `profile.updated_at` и условия операции. В
частности, непосредственно перед ненулевым `stock_update` обязательны
`remote_state='hidden_confirmed'`, непустой `manual_hidden_confirmed_at`,
`enabled=true` и непросроченный run lease; при любом расхождении item отменяется
как stale без вызова Ozon. Это execution-time check, а не только фильтр выборки.
`pending` с отсутствующим/просроченным lease не остаётся навсегда: worker
reclaim-ит исходный run при допустимом retry, либо переводит profile и run item в
`failed` с причиной `stale_pending_run`.

### Таблица переходов состояния

`remote_state` не является индикатором свежести: за неё отвечают
`content_dirty` и `stock_dirty`. Переходы выполняет только worker/серверная
команда, а не браузер.

| Событие | Новое состояние | Действие |
|---|---|---|
| Создан или изменён enabled-профиль; оператор ставит content-import | `pending` | Создать run; при re-import сначала отправить stock `0`. |
| Import принят Ozon | `awaiting_moderation` | Сохранить task/product id, остаток `0`, `moderation_started_at`, запланировать read-only polling. |
| `moderation_poll` вернул `MODERATED` | `awaiting_manual_hide` | Показать оператору шаг скрытия в ЛК. |
| `moderation_poll` вернул отклонение/validation failed | `failed` | Сохранить безопасную причину; оператор правит контент и запускает новый import. |
| Poll временно не дал конечного статуса до дедлайна | `awaiting_moderation` | Сохранить `last_moderation_checked_at`; повторить с backoff. |
| Достигнут `OZON_MODERATION_MAX_AGE_HOURS` без конечного статуса | `failed` | Сохранить `moderation_timeout` и alert оператору. |
| Оператор подтверждает скрытие | `hidden_confirmed` | Записать actor/time и audit event; это не вызов `visibility/set`. |
| Успешный `stock_update` | без смены | Перед ненулевым stock проверить API-признак скрытия, если он доступен; иначе записать метод `operator` (honor-system). Затем сохранить `last_stock_sent_quantity`, `stock_synced_at`, снять `stock_dirty`. |
| Контент изменён | без смены, но подтверждение очищено | Поставить `content_dirty/stock_dirty`; scheduler не вправе вернуть ненулевой stock. |
| Профиль отключён | `disabled` | Поставить `stock_dirty=true`; zero-stock выбирает его по `ozon_product_id` и последнему stock. |
| Disabled-профиль включён снова | `not_synced` | Очистить подтверждение скрытия, поставить content/stock dirty; выполнить новый import с `0`, модерацию и повторное ручное скрытие. |
| Ошибка локальной readiness-валидации | `invalid` | В Ozon HTTP не выполнять; показать поля для исправления. |
| Невосстановимая ошибка Ozon/retry исчерпан | `failed` | Сохранить безопасный code/message; повтор возможен по кнопке. |

### Настройки доставки

В уже существующей карточке Ozon (`/admin/settings/delivery`) добавить
подраздел «FBS-склад Ozon»:

- список складов загружается сервером с Ozon через `/v2/warehouse/list` с
  cursor-pagination;
- оператор выбирает ровно один уже созданный склад;
- сохраняются id и отображаемое имя;
- отсутствие выбранного склада — блокирующая ошибка для live sync;
- склад нельзя создавать, менять или удалять из приложения.

Перед сохранением выполнить read-only запрос к Ozon и проверить, что выбранный
склад существует и имеет тип `fbs`. `delivery-method/list` не использовать как
проверку пригодности: discovery показал, что он относится к realFBS и для этого
склада возвращает пустой список. Пригодность для Ozon Доставки подтверждается
контролируемым product/stock smoke.

### Панель синхронизации Ozon (Доставка → Ozon)

В карточке Ozon на `/admin/settings/delivery` добавить панель с двумя блоками и
видимым статусом/деталями:

**Товары МАВИТА → Ozon (загрузка/актуализация):**
- сводка: сколько профилей `enabled`, готовы (readiness ok), ожидают модерации,
  ожидают ручного скрытия, подтверждённо скрыты (`hidden_confirmed`), требуют
  content/stock sync, `invalid`/`failed`; возраст последнего content-import и
  последнего stock-update;
- кнопки: «Проверить готовность всех» (dry-run, Ozon не вызывается),
  «Загрузить готовые в Ozon» (массовый import с `confirm=true`; на Ozon уходит
  нулевой остаток), «Подтвердить скрытие в ЛК» (для прошедшей модерацию карточки,
  сохраняет только actor/time), «Проверить модерацию» (read-only) и «Обновить
  остатки» (только stock только для подтверждённо скрытых карточек);
- статус текущего/последнего run (`queued/running/completed/failed`), счётчики,
  ссылка на детали run;
- детали run: построчно по товарам — `offer_id`, этап (`awaiting_moderation`,
  `awaiting_manual_hide`, `hidden_confirmed`), результат/время проверки
  модерации, отметка ручного подтверждения и метод проверки скрытия, записанный
  **только успешным `stock_update`**, безопасная ошибка, время; **без секретов**.

После изменения контента UI явно предупреждает: повторный import сначала
обнулит FBS-остаток, затем карточку снова нужно скрыть и подтвердить. Для серии
правок оператор может сохранить их и выполнить один ручной массовый import, а не
запускать import после каждого сохранения.

**ПВЗ Ozon → магазин (каталог пунктов):**
- статус последней синхронизации каталога (`ozon_catalog_sync`): success/failed,
  время, число активных точек, свежесть (гейт 48 ч);
- кнопка ручного запуска синхронизации ПВЗ и «Проверить связь»;
- детали последнего прохода: overlap, скрытые/восстановленные точки, причина
  при `failed`.

Панель только отображает и запускает; HTTP к Ozon идёт через серверные endpoints,
ключи в браузер не попадают.

### Изображения

Изображения берутся из `product_images` в текущем порядке. URL формируется как
`NEXT_PUBLIC_BASE_URL + /uploads/products/<filename>` и обязан быть публичным
HTTPS URL, доступным серверам Ozon без cookies, VPN и авторизации. На localhost
синхронизация изображений запрещена и возвращает понятную ошибку. Нет ни одного
изображения — профиль не готов к синхронизации.

## Правила готовности товара

Перед live sync сервер формирует список ошибок. Товар нельзя отправить, если
хотя бы одно условие не выполнено:

- `enabled=true`;
- заполнены name, description, текущая цена и минимум одно изображение;
- выбрана пара `description_category_id` + `type_id`;
- заполнены все обязательные для выбранной Ozon категории атрибуты;
- штрихкод: **первый import** новой карточки без `ozon_product_id` допускается
  без штрихкода, поскольку живой smoke подтвердил автогенерацию Ozon; **каждый
  последующий import** требует штрихкод, сохранённый из ответа Ozon либо
  введённый оператором;
- заполнены вес и все три габарита;
- задан FBS-склад;
- установлен `NEXT_PUBLIC_BASE_URL` с HTTPS.
- `compliance_status='ready'`: оператор проверил для категории требования Ozon
  к модерации и, если применимо, подготовил/внёс в ЛК сертификат или декларацию.

Подключение к «Ozon Логистика и Select» и API-скрытие в readiness **не входят**:
приложение не скрывает карточку само. Перед массовой загрузкой UI показывает
оператору явное предупреждение: «карточка будет публичной с остатком 0; после
модерации скройте её вручную в ЛК (бейдж „Ozon Доставка“), подтвердите скрытие
здесь и только затем выставляйте остаток».

`visibility` товара на сайте не влияет на возможность sync: скрытый товар может
быть подготовлен заранее. В следующей фазе создавать доставку разрешено только
для товара, доступного покупателю на сайте, с достаточным
`fbs_stock_quantity`; точка списания/восстановления лимита определяется в
спеке жизненного цикла отправления.

## Синхронизация

### Направление и триггеры

Синхронизация строго односторонняя: **МАВИТА → Ozon**. Из Ozon разрешено читать
только справочники, статус импортов и состояние выбранного склада. Входящие
цены, описания, остатки и изображения Ozon никогда не перезаписывают сайт.

Запуски:

1. ручной dry-run одного товара;
2. **ручная загрузка/обновление карточки** одного товара (по кнопке оператора) —
   это единственный путь создания/изменения карточки, т.к. оно может сделать
   карточку публичной. Import всегда оставляет/ставит FBS-остаток `0`, затем
   требует модерации и ручного скрытия в ЛК;
3. **ручной массовый запуск** загрузки готовых enabled-профилей (по кнопке, с
   `confirm` и предупреждением о публичности с остатком `0`);
4. фоновая CLI-задача по расписанию — **только обновление FBS-остатка** уже
   загруженных карточек c `remote_state='hidden_confirmed'`,
   `manual_hidden_confirmed_at IS NOT NULL` и `stock_dirty=true`; **не** делает
   re-import контента и **не** меняет видимость. Отдельная zero-stock-задача
   включает ранее синхронизированные `disabled` профили. Неподтверждённым
   карточкам расписание ненулевой остаток не отправляет;
5. отдельная фоновая read-only задача `moderation_poll` (и ручная кнопка
   «Проверить модерацию») опрашивает только `awaiting_moderation`; она не
   импортирует контент, не пишет остаток и не меняет видимость. После
   `OZON_MODERATION_MAX_AGE_HOURS` без конечного статуса она переводит профиль
   в `failed` и уведомляет оператора;
6. после изменения товара UI показывает «требует синхронизации», но не вызывает
   Ozon из HTTP-запроса сохранения формы.

Требование к CLI: одна активная задача одновременно, lease/fencing в БД,
ограниченный параллелизм, timeout, retry только для сетевых и `429/5xx` ошибок с
exponential backoff. Ошибки в одном товаре не отменяют весь запуск.

### Алгоритм одного товара

1. В транзакции прочитать `products`, `product_images`, профиль и настройки
   склада; заблокировать profile от параллельной sync.
2. Провалидировать readiness. При ошибке записать `remote_state='invalid'` и
   структурированную причину, HTTP к Ozon не выполнять.
3. Сформировать детерминированный payload из сайта:
   `offer_id`, название, описание, `description_category_id`, `type_id`,
   атрибуты, URL изображений, вес,
   габариты, штрихкод и цена в строковом денежном формате. Import не передаёт
   флаг видимости и не вызывает `visibility/set`.
4. Если карточка ранее была `hidden_confirmed` с ненулевым остатком, сначала
   выполнить `zero_stock` на snapshot FBS-складе. Затем вызвать актуальный
   import/upsert API Ozon. Не создавать второй товар при повторе: использовать
   стабильный `offer_id` и idempotency key, если метод его поддерживает.
5. Если импорт асинхронный, сохранить task id и опрашивать только статус import
   в рамках допустимого таймаута. Не считать отправку payload успешной
   синхронизацией до подтверждённого статуса Ozon и получения `ozon_product_id`.
6. Для новой карточки после import установить на snapshot выбранного FBS-склада
   остаток `0`, если он ещё не равен нулю, сохранить
   `remote_state='awaiting_moderation'` и завершить run. Worker не ждёт
   модерацию: отдельный `moderation_poll` читает product-info с bounded backoff.
   `MODERATED` переводит карточку в `awaiting_manual_hide`; отклонение модерации
   или validation failed переводит её в `failed` с безопасной причиной.
7. `confirm-hidden` доступен только для `awaiting_manual_hide`; он сохраняет
   actor/time и переводит карточку в `hidden_confirmed`. Если discovery нашёл
   читаемый признак скрытия, сервер обязан проверить его непосредственно перед
   активацией ненулевого остатка и записать метод `api`; иначе UI прямо помечает
   подтверждение как `operator` (honor-system). Только отдельный `stock_update`
   после этого вправе передать `fbs_stock_quantity` (или `0` при отключении).
   `hidden_verified_at` и `hidden_verification_method` записывает только
   успешный `stock_update`. На успехе обновить соответствующий
   `content_synced_at` или `stock_synced_at`, ids и очистить ошибку. На ошибке
   сохранить безопасные code/message без request headers, ключей и персональных
   данных.

Изменение карточки или FBS-лимита во время sync не теряется: после выполнения
сравнить `products.updated_at`/`profile.updated_at` со snapshot. Если они новее
snapshot, выставить соответствующий `content_dirty` или `stock_dirty`; после
content-изменения также сбросить подтверждение скрытия и оставить остаток `0`.

### Отключение товара

Выключение `enabled` не удаляет карточку Ozon. Оно ставит локальный profile в
`disabled` и ставит FBS-остаток `0` при следующем zero-stock запуске (он обязан
выбирать ранее импортированные disabled-профили). Нулевой остаток убирает товар
из продажи, не публикуя и не удаляя карточку.
Полностью убрать карточку с витрины оператор может вручную в ЛК (скрытие или
архив) — приложение этого не делает. Удаление карточки запрещено.

## HTTP-контракты приложения

Все endpoints находятся под существующей admin авторизацией и возвращают
унифицированный JSON error contract приложения.

| Endpoint | Назначение |
|---|---|
| `GET /api/admin/ozon/warehouses` | Серверный список доступных FBS-складов без секретов. |
| `GET /api/admin/ozon/description-categories` | Серверное дерево категорий для выбора пары `description_category_id` + `type_id`. |
| `GET /api/admin/ozon/description-categories/:id/attributes` | Серверный список атрибутов и допустимых значений для выбранной пары категории/type. |
| `PATCH /api/admin/settings/delivery` | Расширяется полями выбранного склада Ozon; остаётся атомарным. |
| `GET /api/admin/products/:id/ozon-profile` | Profile и status без секретов. |
| `PATCH /api/admin/products/:id/ozon-profile` | Валидация и сохранение технических полей. |
| `POST /api/admin/products/:id/ozon-profile/dry-run` | Возвращает readiness и план действия, Ozon не вызывается. |
| `POST /api/admin/products/:id/ozon-profile/import` | Ставит single-item import; остаток на карточке остаётся/становится `0`. |
| `POST /api/admin/products/:id/ozon-profile/check-moderation` | Ставит/выполняет read-only проверку product-info для `awaiting_moderation`. |
| `POST /api/admin/products/:id/ozon-profile/confirm-hidden` | Аудируемо подтверждает ручное скрытие после модерации; не вызывает `visibility/set`. |
| `POST /api/admin/products/:id/ozon-profile/stock-sync` | Ставит stock-only или zero-stock задачу; ненулевой остаток требует `hidden_confirmed`. |
| `POST /api/admin/ozon/catalog-sync` | Ставит массовый content-import с нулевым остатком; требует явного `confirm=true`. |
| `POST /api/admin/ozon/catalog-stock-sync` | Ставит массовый stock-only run только для `hidden_confirmed` профилей. |
| `GET /api/admin/ozon/catalog-sync/:runId` | Статус и итог массового запуска. |

Долгая массовая синхронизация не выполняется внутри request lifecycle. Endpoint
создаёт run в БД, а worker/CLI его подхватывает по lease/fencing-модели из
миграции `011`.

## Feature gate checkout

Текущая реализация умеет искать ПВЗ Ozon, но не создаёт Ozon-заказ. Поэтому
предлагать Ozon покупателю сейчас запрещено.

Добавить env-флаг:

```env
OZON_LOGISTICS_ORDER_FLOW_ENABLED=false
OZON_CATALOG_SYNC_ENABLED=false
OZON_MODERATION_MAX_AGE_HOURS=168
```

`resolveDeliveryMode()` и `getLockedDeliverySnapshot()` обязаны исключать
перевозчик `ozon`, когда флаг не равен literal `true`, независимо от
`ozon_pickup_enabled`, ключей и свежести каталога ПВЗ. В админке рядом с Ozon
показывать предупреждение «ПВЗ синхронизированы, но оформление отправления ещё
не реализовано». Следующая фаза может открыть флаг только после end-to-end
реализации order create/cancel и успешного тестового отправления.

`OZON_CATALOG_SYNC_ENABLED` — отдельный dark-gate каталога. Пока он не равен
literal `true`, все мутационные catalog endpoints (`import`, `stock-sync`,
`confirm-hidden`, массовые runs) и worker отказываются выполнять live-вызовы
Ozon; dry-run, чтение складов/категорий, polling модерации и просмотр статусов
остаются доступны. Включать его разрешено только после успешного smoke import,
poll модерации, проверки скрытия и записи FBS-остатка.

`OZON_MODERATION_MAX_AGE_HOURS` ограничивает жизнь `awaiting_moderation`; при
некорректном или отсутствующем значении применяется безопасный default `168`.

## Безопасность и наблюдаемость

- Api-Key, Client-Id, Authorization headers и полные HTTP payloads не логируются.
- В UI показываются только идентификаторы товара/склада, состояние и безопасная
  причина ошибки.
- Все значения из Ozon валидируются схемой до записи в БД.
- URL изображений разрешены только `https:` и домен собственного магазина;
  SSRF через произвольный URL невозможен.
- Операторские действия пишутся в audit event / sync run с login timestamp, но
  без ключей и без данных покупателей.
- Rate limit и backoff учитывают документированные ограничения Ozon. `429` не
  ретраится мгновенно.
- Фоновый job должен иметь метрики: число готовых/синхронизированных/failed,
  возраст последней успешной sync и число профилей с нулевым остатком.

## Тестирование

Обязательны:

1. SQL migration tests для `010` и `011`: constraints,
   offer_id/barcode uniqueness, cascade, default `fbs_stock_quantity=0` и
   lease/fencing очереди.
2. Unit tests для validation: отрицательный остаток, нет фото, габаритов,
   категории, штрихкода у уже импортированной карточки, склада, HTTPS base URL,
   обязательного attribute; первый import без штрихкода допустим только при
   подтверждённой способности Ozon сгенерировать его.
3. Unit tests преобразования денег: копейки → строка в рублях; без float и
   с корректной активной скидкой.
4. HTTP-client tests через mock `fetch`: success, async import, `400`, `401`,
   `403`, `429`, `5xx`, timeout и malformed response.
5. Idempotency tests: два запуска одной позиции не создают второй offer; import
   всегда оставляет stock `0`, а ненулевой stock невозможен до статуса
   `hidden_confirmed`.
6. Tests admin auth и подтверждения массовой sync.
7. Tests feature gate: при выключенном
   `OZON_LOGISTICS_ORDER_FLOW_ENABLED` Ozon не возвращается checkout API и
   прямой create order не может выбрать `ozon_pickup`.
8. Integration smoke с боевым ключом и явного разрешения владельца: один тестовый
   товар, один FBS-склад — import по кнопке с остатком `0`, проверка
   `product_id`/модерации, ручное скрытие в ЛК, аудируемое подтверждение в
   админке, затем запись и проверка FBS-остатка. После теста — stock `0`.
9. Tests: фоновое расписание делает только stock-update/zero-stock и read-only
   moderation_poll, но не вызывает content-import или visibility; оно не выбирает
   неподтверждённые карточки, а zero-stock включает disabled. После re-import
   подтверждение скрытия сбрасывается; ручная загрузка карточки доступна только
   из admin-кнопки.
10. Tests readiness: отсутствие `compliance_status='ready'`, а также отсутствие
    обязательных для свечей сертификата/декларации в ЛК блокирует import.
11. Tests state-machine: `pending` используется только во время import; polling
    переводит `awaiting_moderation` в `awaiting_manual_hide` только при
    `MODERATED`, а отклонение/validation failed — в `failed` с безопасной
    причиной. Poll не отправляет import, stock или visibility.
12. Tests скрытия: при доступном API-признаке ненулевой stock отклоняется, если
    product-info не подтверждает скрытие; при отсутствии признака UI/API явно
    возвращает метод `operator` и audit record. Ни один путь не называет
    honor-system автоматической верификацией.
13. Tests dark-gate: при `OZON_CATALOG_SYNC_ENABLED=false` ни HTTP endpoint, ни
    worker не делает мутационный вызов Ozon; dry-run и read-only polling доступны.
14. Concurrency tests: stock-run выбирает карточку, затем concurrent re-import
    сбрасывает подтверждение; execution-time re-check под lock отменяет item и
    не отправляет ненулевой stock. Проверить также reclaim/`stale_pending_run`.
15. Tests moderation deadline: poll до дедлайна остаётся read-only, а после
    `OZON_MODERATION_MAX_AGE_HOURS` ставит `failed`/alert без stock-write.
16. Tests lifecycle: `blocked` и `not_checked` блокируют import; re-enable
    disabled-профиля очищает подтверждение и требует нового import с `0`.

## Критерии приёмки

Фаза завершена, когда одновременно выполнены все пункты:

- оператор выбирает существующий FBS-склад и не может включить live sync без него;
- для товара можно заполнить профиль, увидеть все недостающие поля в dry-run и
  безопасно синхронизировать его;
- повторный sync не создаёт дубль в Ozon;
- import создаёт/обновляет карточку только с остатком `0`; ненулевой остаток
  возможен лишь после MODERATED, ручного скрытия и подтверждения в админке;
- `awaiting_moderation` не зависает: read-only polling или ручная проверка
  переводит MODERATED в шаг ручного скрытия, а отклонённую модерацию — в понятный
  `failed` с возможностью исправить контент и повторить import;
- Gate-0 документально подтверждает доступность ручного скрытия в ЛК для текущего
  аккаунта; при его недоступности live-sync не реализуется и не включается;
- execution-time re-check не позволяет stale stock-run отправить ненулевой
  остаток после re-import/сброса подтверждения;
- фактический лимит на выбранном FBS-складе совпадает с `fbs_stock_quantity` у
  подтверждённо скрытой карточки;
- отключение профиля приводит к нулевому остатку и не удаляет remote карточку;
- перед публичной загрузкой UI явно предупреждает, что карточка станет видимой с
  остатком `0`, её нужно скрыть в ЛК и подтвердить это до активации остатка;
  статус/детали синхронизации (товары и ПВЗ) видны в админке;
- товар не попадает в import без проверки требований модерации и готовности
  требуемого сертификата/декларации;
- выбранный в discovery способ проверки скрытия соблюдён: API-признак проверяется
  перед ненулевым stock, а при его отсутствии UI явно показывает honor-system;
- ключи нигде не раскрываются;
- все новые тесты, typecheck и lint проходят;
- при любом состоянии этой фазы Ozon не может быть выбран на checkout, пока
  `OZON_LOGISTICS_ORDER_FLOW_ENABLED=false`.

## Rollout

0. **До написания кода, миграций и деплоя пройти Gate-0:** на существующей
   тестовой карточке оператор вручную находит и применяет скрытие с витрины в
   ЛК. Зафиксировать доступность действия и результат («Ozon Доставка»). Если
   ЛК показывает требование «увеличьте продажи»/подключение к программе или не
   даёт скрыть карточку, остановить эту фазу до нового решения владельца —
   сценарий «import + ручное скрытие» невалиден.
1. В ЛК Ozon создать FBS-склад и убедиться, что `/v2/warehouse/list` его
   возвращает; до этого rollout не начинается.
2. Применить миграции `010`/`011` и задеплоить code с выключенным feature gate;
   `products.in_stock` и checkout при этом не меняются.
3. Выбрать существующий FBS-склад, заполнить технические профили для 1–2
   тестовых товаров и указать точные FBS-остатки.
4. До включения `OZON_CATALOG_SYNC_ENABLED` выполнить read-only discovery на
   тестовой карточке: зафиксировать поле статуса модерации и наличие либо
   отсутствие читаемого признака скрытия. При отсутствии признака согласовать
   honor-system в UI как операционный риск.
5. Проверить для тестового товара требования модерации Ozon и подготовить/внести
   в ЛК сертификат или декларацию, если это требуется для его категории.
6. Включить `OZON_CATALOG_SYNC_ENABLED` только на время контролируемого smoke.
   Выполнить dry-run, затем **оператор по кнопке** заливает single-item с
   остатком `0`, проверяет в ЛК создание карточки и дожидается `MODERATED`.
   После этого вручную скрывает её в ЛК (бейдж «Ozon Доставка»), подтверждает
   скрытие в админке и только затем отправляет ненулевой остаток.
7. Запустить массовый import только после успешного single-item; каждая карточка
   остаётся с остатком `0` до отдельного ручного скрытия и подтверждения.
   Массовый stock-sync запускать только после завершения этих подтверждений.
8. Включить фоновое обновление остатка по расписанию (только остаток, не контент)
   только для `hidden_confirmed` карточек.
9. Мониторить ошибки и возраст синхронизации. Не включать Ozon на checkout в
   рамках этого rollout. Подключение к «Ozon Логистика и Select» (для будущего
   API-скрытия) — отдельная инициатива, когда программа станет доступна.

## Следующая фаза

После приёмки этой фазы отдельно спроектировать и реализовать жизненный цикл
заказа Ozon: availability/checkout, `order/create` только после подтверждённой
оплаты, идемпотентность с `orders.id`, отмена, статусы, этикетки, выдача трека,
возвраты и условие включения Ozon на checkout. Эта фаза потребует отдельного
review API-прав; текущий ключ `Product`/`Warehouse` нельзя автоматически
расширять до Admin.
