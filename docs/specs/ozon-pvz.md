# Интеграция OZON — выбор ПВЗ при оформлении заказа

Статус: **реализовано (2026-06-21), архитектура скорректирована по живому API.**

> ## Поправка после проверки живым ключом (2026-06-21)
> Исходное предположение «как у СДЭК: `point/list`+`point/info` достаточно для
> живого поиска по городу» **оказалось неверным**. Реальный контракт:
> - `POST v1/delivery/point/list` → `{ points:[{ map_point_id, coordinate }] }` —
>   ТОЛЬКО id+координаты, ~90 000 точек, без города/адреса/названия;
> - `POST v1/delivery/point/info` — тело строго `{ map_point_ids:[int] }` (1…100 за
>   раз); детали под `delivery_method` (`address`, `address_details{city,region,…}`,
>   `name`), причём **`map_point_id` лежит ВНУТРИ `delivery_method`**, а `city`
>   часто пуст (берём из разбора `address`/region).
>
> Поэтому клиентский поиск ПВЗ Ozon — **не живой прокси**, а **локальный каталог**:
> - таблица `ozon_pickup_points` + состояние `ozon_catalog_sync` (миграции `008`,`009`);
> - синхронизация `scripts/sync-ozon-pickup-points.ts` (`npm run delivery:sync-ozon`):
>   `point/list` → батчи `point/info` ≤100 → парс города → upsert; помечает все id
>   прохода `run_id`. Финализация НЕ деструктивна: считает реальный overlap (под
>   блокировкой, в одной транзакции), при расхождении > 2% активных — `failed` без
>   изменений + алерт; иначе СКРЫВАЕТ (`active=false`, обратимо), а не удаляет, точки,
>   отсутствующие два прохода подряд (`missed_runs`). Таймаут/ретраи/fencing по
>   `run_id`; состояние — в `ozon_catalog_sync` (с поколением `last_success_at`);
> - `/api/ozon` ищет ПО ЛОКАЛЬНОМУ каталогу (префикс `lower(city)`, индекс), не живьём;
> - `getPickupPoint` (re-confirm при заказе) — живой `point/info` по одному id;
> - **гейт свежести**: включить Ozon и предлагать на checkout можно только при
>   успешной полной синхронизации не старше 48 ч (`resolveDeliveryMode`,
>   `saveCarrierSettings`); несвежий каталог убирает Ozon, СДЭК не трогает.
>
> Разделы ниже про `listPickupPoints(city)` как клиентский поиск читать с этой
> поправкой: живой `listPickupPoints` остался лишь как пинг «Проверить связь».

Предпосылка — исследование [ozon-wb-pickup-points.md](ozon-wb-pickup-points.md):
у Ozon есть сервис «Ozon Доставка» (Ozon Логистика) для сторонних магазинов с
публичным API и сетью 85 000+ ПВЗ; у Wildberries аналога нет. Поэтому
реализуем **только Ozon**.

Связанные документы: [cdek-pvz.md](done/cdek-pvz.md) (реализованная СДЭК-интеграция —
эталон, который обобщаем), [delivery-options.md](delivery-options.md) (порядок
развития, Ozon — второй ПВЗ-перевозчик), [admin-orders.md](done/admin-orders.md)
(модель заказа), [legal-business-guide.md](../legal-business-guide.md) (статус
продавца, ПДн).

## Цель

Добавить на checkout опцию **«Заберу из ПВЗ ОЗОН»** наравне с уже существующим
«Пункт выдачи СДЭК»: покупатель выбирает перевозчика, ищет пункт, оформляет и
оплачивает заказ одной суммой через Робокассу. Код и адрес ПВЗ сохраняются в
нейтральный delivery-snapshot заказа и показываются покупателю и в админке.

## Главное архитектурное наблюдение

Документы называют модель доставки «нейтральной», но в коде это **наполовину
правда**. Колонки БД действительно нейтральные, а вот логика и ограничения
жёстко завязаны на СДЭК. Чтобы Ozon стал *вторым* перевозчиком, нужно обобщить
ровно эти места:

| Слой | Сейчас (захардкожен СДЭК) | Что нужно |
|---|---|---|
| Колонки `orders` | `delivery_method`, `delivery_carrier`, `pickup_point_*` — уже нейтральны ✅ | без изменений |
| CHECK `orders_delivery_method_check` | разрешает только `('cdek_pickup','cdek')` ❌ | новая миграция: разрешить `('ozon_pickup','ozon')` |
| CHECK `orders_pickup_point_snapshot_check` | условие `delivery_method = 'cdek_pickup'` ❌ | обобщить на любой `*_pickup` |
| `store_settings` | один тариф `cdek_pickup_delivery_kopecks` ❌ | тариф на перевозчика (см. ниже) |
| `lib/orders.ts` `OrderInput.delivery.method` | литерал `'cdek_pickup'` ❌ | объединение `'cdek_pickup' \| 'ozon_pickup'` |
| `lib/orders.ts` `createOrder` | читает `cdek_pickup_delivery_kopecks`, пишет `'cdek'`/`'cdek_pickup'` | выбирать тариф и carrier по выбранному способу |
| `robokassa/init` | принимает только `method === 'cdek_pickup'` ❌ | принять оба способа |
| `checkout/page.tsx` | UI и тексты «СДЭК» захардкожены ❌ | селектор перевозчика + два источника ПВЗ |
| `/api/checkout/delivery` | отдаёт `cdekPickupDeliveryKopecks` | отдавать список доступных перевозчиков с тарифами |
| `lib/cdek.ts` + `/api/cdek` | прокси к СДЭК | новый брат `lib/ozon.ts` + `/api/ozon` |

Вывод: **это не «ещё одна интеграция с нуля», а обобщение СДЭК-слоя + второй
прокси.** Колонки заказа переиспользуются как есть.

## Решения (зафиксировать перед реализацией)

| Вопрос | Решение |
|---|---|
| Модель выбора | **Перевозчик настраивается в админке** (вкл/выкл + тариф на каждого). Если включён один — показываем сразу его без селектора; если оба — покупатель выбирает СДЭК или ОЗОН. Это покрывает и «Ozon вместо СДЭК», и «оба вместе» без новой развилки в коде. |
| Тариф | **Фиксированный или бесплатный**, как у СДЭК — отдельная сумма на перевозчика. Без живого расчёта по габаритам. Габариты/вес в `products` не добавляем. |
| Денежный поток | Тот же, что у СДЭК (см. ниже): покупатель платит магазину одну сумму, магазин отдельно платит Ozon. |
| Создание отправления | v1 — **вручную в ЛК Ozon**, как с СДЭК. Авто-создание через Seller API — отдельный этап. |
| Боевой режим | Требует кабинета продавца Ozon (FBO/FBS), private application и боевых ключей `Client-Id`/`Api-Key`. До этого Ozon выключен в админке. |

## Хватает ли текущих данных клиента? — Да

Сценарий ПВЗ у Ozon требует ровно тех же данных, что уже собирает checkout для
СДЭК, и они уже есть в модели заказа:

| Нужно для ПВЗ Ozon | Где уже есть |
|---|---|
| ФИО получателя | `orders.customer_name` |
| Телефон получателя (нормализован `+7…`) | `orders.customer_phone` (`normalizePhone` в `lib/orders.ts`) |
| Email покупателя | `orders.customer_email` |
| Выбранный пункт: код, город, название, адрес | нейтральные `pickup_point_code/city/name/address` |

**Новых полей покупателя не нужно.** Для будущего авто-создания отправления через
Seller API Ozon потребует имя + телефон получателя и код ПВЗ — всё это у нас
есть. Адрес двери нужен только для курьерского сценария — он вне этой спеки
(см. «мир до двери» в [delivery-options.md](delivery-options.md)).

## Что предоставляет Ozon

- **Seller API «Ozon Логистика»**, авторизация заголовками `Client-Id` + `Api-Key`.
- Список ПВЗ/постаматов: `POST v1/delivery/point/list` (полный список — хранить у
  себя, обновлять во 2-й половине дня, т.к. список меняется ежедневно).
- ПВЗ для карты: `POST v1/delivery/map`. Информация о конкретном пункте:
  `v1/delivery/point/info`.
- Создание отправления / печать этикетки / статусы / возвраты — методы Seller API
  для Ozon Логистики (на этап авто-оформления).
- Покрытие 85 000+ точек; комиссии за продажу нет, платится только логистика.

В нашей v1 карты/виджета нет: покупатель ищет ПВЗ по городу через наш прокси
`/api/ozon` и выбирает пункт из списка — тот же UX, что у СДЭК. `Api-Key`
остаётся только на сервере.

## Денежный поток (идентичен СДЭК)

Два независимых потока; покупатель в расчётах с Ozon не участвует.

```
Покупатель → (товары + доставка) → Робокасса → магазин   (одна предоплата)
Магазин    → оформляет отправление (ЛК Ozon, v1)          → сдаёт в ПВЗ Ozon
Ozon       → счёт по логистике                            → магазин платит Ozon
```

Тариф последней мили Ozon для сторонних магазинов с 04.06.2026 —
**фикс. 30 ₽ за товар** (возможно акция, проверять в ЛК). Это себестоимость
магазина. В заказе покупателю показываем **свою** фикс-цену доставки (с запасом)
или 0 (бесплатно) — ровно как с СДЭК. Инвариант I10
(`items_kopecks + delivery_kopecks = total_kopecks`) сохраняется; снимок цены не
пересчитывается после оплаты.

## Анализ тарифов и рекомендуемая цена доставки (первые 3 месяца)

> Срок действия: калибровочный период **2026-06 … 2026-09**. Пересмотреть после
> первых реальных отправок и подтверждения тарифа Ozon в ЛК.

### Себестоимость для магазина

Формула: `30 ₽ × кол-во товаров + ~25 ₽ последняя миля за заказ` (на 2026-06).
«За товар» = за единицу — **подтвердить в ЛК** (наборы как один SKU могут считаться
иначе).

| Товаров в заказе | Себестоимость сейчас (30 ₽/шт) | Если тариф вырастет ×2 (60 ₽/шт) |
|---|---|---|
| 1 | ~55 ₽ | ~85 ₽ |
| 2 | ~85 ₽ | ~145 ₽ |
| 3 | ~115 ₽ | ~205 ₽ |
| 4 | ~145 ₽ | ~265 ₽ |

### Что поддерживает код

Только **фикс-сумма на перевозчика** или **0 (бесплатно)**. Порогов («бесплатно от
N ₽») и расчёта по габаритам нет — это сознательное упрощение модели.

### Маржа магазина при разных фикс-ценах (тариф 30 ₽/шт)

| Товаров | при цене 149 ₽ | при цене 199 ₽ | при цене 249 ₽ |
|---|---|---|---|
| 1 | +94 ₽ | +144 ₽ | +194 ₽ |
| 2 | +64 ₽ | +114 ₽ | +164 ₽ |
| 3 | +34 ₽ | +84 ₽ | +134 ₽ |
| 4 | +4 ₽ | +54 ₽ | +104 ₽ |

Стресс-тест при тарифе ×2 (60 ₽/шт): цена 199 ₽ остаётся в плюсе для 1–2 товаров,
уходит в небольшой минус (~−6 ₽) только на заказе из 3 товаров и глубже — на 4.
Цена 149 ₽ при удвоении тарифа убыточна уже с 2 товаров.

### Рекомендация на 3 месяца

**Фиксированная доставка 199 ₽** для ПВЗ ОЗОН.

Обоснование:
- Покрывает себестоимость с запасом для типового заказа (1–2 свечи) даже если
  Ozon поднимет тариф вдвое.
- Запас защищает от того, что снимок цены в оплаченном заказе не пересчитывается
  (I10): рост тарифа Ozon после оформления не превращает старые заказы в убыток.
- Для покупателя 199 ₽ за доставку до ПВЗ — рыночно привычно и не отпугивает.
- Симметрично с СДЭК — единый прайс по перевозчикам упрощает восприятие и админку.

Альтернативы (если приоритет — конверсия, а не маржа доставки):
- **Бесплатно (0 ₽)** — себестоимость (~55–115 ₽/заказ) закладывается в цену
  свечей; хорошо как промо на старте, но прямой убыток на крупных корзинах.
- **149 ₽** — мягче для покупателя, но почти нулевая маржа на 4 товарах и убыток
  при росте тарифа; брать только если средний заказ — 1–2 позиции.

Через 3 месяца: сверить фактические счета Ozon с заложенной ценой и средним
числом товаров в заказе, затем зафиксировать постоянный тариф.

## Архитектура

```
checkout (клиент)
   │  выбор перевозчика → поиск города → список ПВЗ
   │     СДЭК → /api/cdek      ОЗОН → /api/ozon
   ▼
/api/ozon (новый прокси) ──Client-Id+Api-Key──► api-seller.ozon.ru (v1/delivery/*)
   │  (Api-Key только на сервере)
   ▼
выбран ПВЗ → {carrier, code} в state
   ▼
POST /api/robokassa/init → createOrder ──повторная проверка кода──► Ozon API
   ▼
orders (нейтральный snapshot: carrier='ozon', method='ozon_pickup', pickup_point_*)
```

## Шаги реализации

### 1. Конфиг и секреты — `shop/.env.example`
```
OZON_API_BASE=https://api-seller.ozon.ru
```
Боевые `Client-Id`/`Api-Key` хранятся только в зашифрованных настройках доставки
из [admin-delivery-settings.md](admin-delivery-settings.md), не в `.env`.
Без ключей Ozon автоматически считается недоступным и в админке не включается.

### 2. `shop/lib/ozon.ts` — брат `lib/cdek.ts`
- Тот же контракт `PickupPoint = { code, city, name, address }` и
  `OzonValidationError(message, unavailable)`.
- `listPickupPoints(city)` → `v1/delivery/point/list` (+ фильтр по городу),
  `getPickupPoint(code)` → `v1/delivery/point/info` для повторной проверки кода
  перед созданием заказа.
- Авторизация заголовками `Client-Id`/`Api-Key` (не OAuth, в отличие от СДЭК — у
  Ozon постоянный ключ, кэш токена не нужен).
- Модуль не ходит в БД и не создаёт отправления: caller передаёт ему уже
  расшифрованные runtime или draft credentials явным параметром.
- `normalize()` под формат ответа Ozon (поля точки отличаются от СДЭК).

> Рекомендация: вынести общий тип `PickupPoint` и интерфейс провайдера
> (`listPickupPoints`/`getPickupPoint`) в `lib/delivery/` и сделать `cdek.ts` и
> `ozon.ts` его реализациями. Это убирает дублирование и упрощает третьего
> перевозчика (Яндекс).

### 3. `shop/app/api/ozon/route.ts` — брат `/api/cdek`
- Публичный поиск ПВЗ по городу, проксирует список Ozon; `Api-Key` не уходит в
  браузер; при отсутствии конфига — 503 `DELIVERY_UNAVAILABLE`.

### 4. БД — новая миграция `005_delivery_multi_carrier.sql`
Колонки заказа не трогаем. Ослабляем CHECK-ограничения из `003`, чтобы пускать
Ozon, и расширяем `store_settings` на тариф по перевозчику:
```sql
-- orders: разрешить второй перевозчик
ALTER TABLE orders DROP CONSTRAINT IF EXISTS orders_delivery_method_check;
ALTER TABLE orders ADD CONSTRAINT orders_delivery_method_check CHECK (
  (delivery_method IS NULL AND delivery_carrier IS NULL AND delivery_kopecks = 0)
  OR (delivery_method = 'cdek_pickup' AND delivery_carrier = 'cdek')
  OR (delivery_method = 'ozon_pickup' AND delivery_carrier = 'ozon')
);
-- orders_pickup_point_snapshot_check: заменить '= cdek_pickup' на "method LIKE '%_pickup'"
--   (требовать непустые pickup_point_* для любого ПВЗ-способа)

-- store_settings: тариф на перевозчика
ALTER TABLE store_settings
  ALTER COLUMN cdek_pickup_delivery_kopecks DROP NOT NULL,
  ADD COLUMN IF NOT EXISTS ozon_pickup_delivery_kopecks INTEGER,
  ADD COLUMN IF NOT EXISTS cdek_pickup_enabled BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN IF NOT EXISTS ozon_pickup_enabled BOOLEAN NOT NULL DEFAULT false;
-- CHECK: каждый *_delivery_kopecks >= 0; если перевозчик enabled — его тариф,
-- client id и зашифрованный секрет NOT NULL (полный idempotent SQL — в admin spec)
```
Миграция идемпотентна и безопасна для существующих заказов (как `003`).

> Дефолт `cdek_pickup_enabled = false` (а не `true`): иначе строгая CHECK из
> [admin-delivery-settings.md](admin-delivery-settings.md) «enabled ⇒ ключи+тариф
> заданы» отклонила бы существующую singleton-строку, у которой ключи пока в
> `.env`. Перевозчик включается явно через админку после ввода ключей. Подробный
> безопасный порядок миграции — в [admin-delivery-settings.md](admin-delivery-settings.md).

### 5. `shop/lib/store-settings.ts`
- `DeliverySettings` → массив/мапа перевозчиков:
  `{ carriers: { cdek: {enabled, kopecks}, ozon: {enabled, kopecks} }, updatedAt, updatedBy }`.
- `getActiveCarriers()` — только enabled, полностью настроенные и успешно
  расшифрованные DB-credentials; неисправный enabled-carrier переводит delivery в
  `error`/503 по fail-closed правилам основной спеки.
- `saveCarrierSettings` обновляет per-carrier тариф и флаги атомарно.

### 6. `shop/lib/orders.ts`
- `OrderInput.delivery.method`: `'cdek_pickup' | 'ozon_pickup'`; добавить поле
  `carrier`/вывести его из method.
- `validateOrderInput`: «выберите пункт выдачи» для любого активного способа.
- `createOrder`: по выбранному способу взять нужный тариф из locked snapshot
  `store_settings`, повторно подтвердить код через **соответствующий** провайдер
  (`cdek.getPickupPoint` / `ozon.getPickupPoint`) с credentials этого снимка, записать
  `delivery_carrier`/`delivery_method` снимком. Логика `PriceChangedError`,
  `total = items + delivery`, snapshot цен — без изменений.

### 7. `/api/checkout/delivery`
- Возвращать список активных перевозчиков с их тарифами и человекочитаемыми
  названиями (для отрисовки опций), а не один `cdekPickupDeliveryKopecks`.

### 8. Фронт — `shop/app/checkout/page.tsx`
- Если активен один перевозчик — показать его как сейчас (без селектора).
- Если активны оба — radio/`<select>` «Способ получения»: «Пункт выдачи СДЭК» /
  «Заберу из ПВЗ ОЗОН». Выбор перевозчика определяет, какой прокси опрашивается
  (`/api/cdek` или `/api/ozon`) и какой тариф идёт в `expectedDeliveryKopecks`.
- В `init` передавать `delivery: { method, pickupPointCode, expectedDeliveryKopecks }`;
  адрес для snapshot сервер берёт заново из API перевозчика.
- Блокировать отправку, пока перевозчик и ПВЗ не выбраны.

### 9. Робокасса — `shop/app/api/robokassa/init/route.ts`
- Принимать `method ∈ {cdek_pickup, ozon_pickup}` (сейчас всё кроме `cdek_pickup`
  превращается в `'invalid'`).
- Строка доставки в фискальном чеке — по перевозчику: «Доставка СДЭК до ПВЗ» /
  «Доставка ОЗОН до ПВЗ» (сейчас захардкожено «СДЭК»).
- Ловить `OzonValidationError` так же, как `CdekValidationError`.

## Зависимости и риски

- **Блокер включения:** боевые `Client-Id`/`Api-Key` = действующий кабинет
  продавца Ozon. До этого Ozon выключен в админке; режим не требует тестовых ключей.
- **Право торговли:** подтвердить, что свечи МАВИТА можно возить через Ozon
  Доставку при статусе самозанятого/ИП (собственное производство, маркировка) —
  см. [legal-business-guide.md](../legal-business-guide.md).
- **Нужен ли активный FBO/FBS-листинг** (товар на витрине Ozon) ради доступа к
  логистике, или достаточно зарегистрированного продавца — уточнить в ЛК до старта.
- **Тариф 30 ₽/товар** может вырасти (возможно акция) — фикс-цену доставки
  покупателю ставить с запасом, как с СДЭК.
- Формат полей ПВЗ в ответе Ozon отличается от СДЭК — `normalize()` писать под
  реальный ответ API, не по аналогии вслепую.
