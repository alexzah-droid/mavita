# МАВИТА-ШОП ANTIPATTERNS: ловушки drift

Дата: 2026-06-19

Документ адаптирует уроки bootstrap-комплекта под магазин свечей. Цель — заранее назвать типовые провалы, чтобы люди и агенты не повторяли их.

## 1. Подпись Робокассы на клиенте

Форма: MD5-хеш считается в браузерном JS, чтобы «упростить» запрос. Password1 попадает в клиентский код.

Правило: подпись всегда считается в `lib/robokassa.ts` на сервере. Клиент получает только redirect URL. Password1 и Password2 — только в `.env`, никогда в коде.

## 2. Цена как FLOAT

Форма: поле `price NUMERIC(10,2)` или `FLOAT`. Заказ на 3 × 299 ₽ = 896.9999... ₽ в Робокассу уходит 897, в БД остаётся 896.9999 — расхождение в отчётах.

Правило: цены хранятся в копейках как `INTEGER`. Перевод в рубли — только на слое отображения. Инвариант I2 в `PROJECT_CORE.md`.

## 3. Ручная правка index.html

Форма: мелкое исправление текста вносится прямо в `index.html`. Следующая генерация бандла затирает правку.

Правило: `index.html` — генерируемый файл, не редактируется. Исходники живут в директории бандлера. `Мавита - четыре направления (один файл).html` редактировать можно.

## 4. Статус заказа меняется напрямую в БД

Форма: отладка или исправление ошибки — `UPDATE orders SET status = 'paid' WHERE id = 42`. Аудит-следа нет, Робокасса об изменении не знает.

Правило: статус меняется только через API-эндпоинт `/api/robokassa/result` с проверкой подписи. Ручное исправление — отдельная admin-операция с логом. Инвариант I4.

## 5. Фото без записи в БД

Форма: файл загружается через SFTP или `scp` напрямую в `/public/uploads/`. В `product_images` записи нет — фото невидимо для витрины.

Правило: загрузка фото только через `POST /api/upload`, который атомарно кладёт файл и создаёт запись в `product_images`. Инвариант I5.

## 6. ResultURL не проверяет подпись

Форма: `/api/robokassa/result` меняет заказ на `paid` без проверки MD5(OutSum:InvId:Password2). Любой HTTP-запрос к эндпоинту «оплачивает» заказ.

Правило: первое, что делает result-хендлер — верификация подписи. Только потом — обновление статуса. Инвариант I3.

## 7. Один факт в нескольких документах

Форма: цена доставки записана в `architecture.md`, `PROJECT_CORE.md` и в комментарии в коде. Через месяц три версии расходятся.

Правило: главный дом факта указан в `DOCS.md`. Остальные документы ссылаются или явно помечают производность.

## 8. Инвариант без теста

Форма: «подпись только на сервере», «цены в копейках» красиво записаны, но не покрыты тестами. Регрессия не замечается.

Правило: после появления кода каждый инвариант из `PROJECT_CORE.md` должен получить строку в `TESTING_PLAN.md` и тест.

## 9. Пустые документы на будущее

Форма: `docs/environments.md` и `docs/operations.md` создаются пустыми «чтобы были». Устаревают до использования.

Правило: рабочий документ создаётся при появлении предмета. До этого шаблон лежит в `docs/project-bootstrap/templates/`.

## 10. Prod-режим Робокассы без явного подтверждения

Форма: `ROBOKASSA_TEST_MODE=false` выставляется «чтобы проверить». Реальный платёж списан с карты тестировщика.

Правило: переключение на prod-режим — Пауза 1. Требует явного подтверждения владельца. В `dev` и staging всегда `ROBOKASSA_TEST_MODE=true`.

## 11. Системную проблему чинят локальным патчем

Форма: второй раз вручную правят `inv_id` в БД, третий раз добавляют `if`-исключение для «особого» товара.

Правило: второй патч одной природы — сигнал для системного правила или ADR в `docs/decisions.md`.

## 12. Парковка без записи

Форма: «категории товаров добавим потом» — нигде не записано, при каком условии возвращаться.

Правило: «пока не делаем X, вернёмся при Y» — запись в `docs/decisions.md`.
